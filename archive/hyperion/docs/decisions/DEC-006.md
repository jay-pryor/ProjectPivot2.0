# DEC-006: A record module is a function of the working data body; the consumer carries the body between store.load and store.save
Date: 2026-09-15
Status: accepted
Tier: interface

## Context
The `registry` CONTRACT session (SL-01) had to decide how a record module reaches the
stored data. `store` 1.0 loads the whole body of `data.json` and saves a body the caller
supplies (its C-001 promises that body back unchanged); DEC-005 makes `data.json` the one
file holding every record kind. The G2 drawing (`docs/module-map.md`) proposes an edge
`registry → store`, but the map says the manifests are the truth once they exist, and a
manifest may list only what the module imports (CORE-CON-003, *drawn*). Deferring would
have left the first record contract with no shape for its operations, and every later
record module copying whatever `registry` did unrecorded.

## Decision
A record module's operations are functions of the `DataBody` value passed in. A changing
operation returns a new body and the changed record; it never modifies the body it was
given, and it touches only the collections and sequences its contract owns. The consumer
(`views` at SL-01; `workflows` later) holds one working body per open of Pivot: it gets it
from `store.load`, replaces it with what each record operation returns, and passes it to
`store.save` when the user saves. A record module therefore reads nothing from the folder
and writes nothing anywhere; `registry` 1.0 does not import `store`, and its manifest does
not list it. A record module whose records include files in the folder (`reference-register`,
REQ-029) imports `store` for the file operation and nothing else.

## Alternatives considered
### Each record module holds a `DataStore` and loads and saves through it
Rejected because: `data.json` holds every kind (DEC-005), so two record modules each
saving their own copy of the body would overwrite each other's records inside one copy of
Pivot, and the only fix is one owner of the working body, which is this decision by
another route. It also makes every record operation a file write, when the requirements
describe an explicit save with unsaved working state (REQ-005, REQ-079, REQ-080).

### `store` holds the working body and record modules mutate it through `store`
Rejected because: `store` 1.0's `save` takes the body as an argument and its contract says
it sees only envelopes and the header (DEC-005); giving it the working state would widen
its contract mid-slice. SL-02's browser mirror of the working state (REQ-079) will need
`store` to be told of every change, and a body passed by value is the simplest thing to
tell it.

### Record modules mutate the body in place and return nothing
Rejected because: a rejected operation could leave the body half-changed, and "body
unchanged on error" would be a promise about mutation rather than about values; a returned
body makes every error condition's "body unchanged" one deep-equality, which the
partial-failure lens can check.

## Consequences
- Makes easy: testing a record module from an empty body with no folder; composing record
  modules by passing one value through each; SL-02's mirror, which receives each new body.
- Makes hard: an operation that spans record modules (REQ-026, REQ-068) must be composed
  by the consumer, which DEC-004 already requires; copying the changed collection on every
  operation, which DEC-003's scale accepts.
- Locks in: `DataBody` as the value every record contract takes and returns; one working
  body per open, owned by the consumer.

## Reversal
Cost to undo: hours while only `registry` 1.0 exists and no `views`; days once every record
module follows it, since each contract's signatures change (Interface tier each).
Would be triggered by: a body too large to copy per operation within the time a user will
wait; or `store` at SL-02 needing to own the working state to keep the browser mirror
honest, in which case the mirror's contract decides and this record is superseded.
