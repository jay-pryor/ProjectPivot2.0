# DEC-005: The baseline fixes the file envelope, folder layout, and record header; each record kind's fields belong to its module's contract
Date: 2026-09-14
Status: accepted
Tier: baseline

## Context
The BASELINE session instantiating `baseline/` (CHG-001) had to write the persisted data
schema, because any change to its shape is a stop condition outside a BASELINE session and
G2 named it baseline (`docs/module-map.md`). G3 had already decided the parts that cross
modules: a save stamp compared on save (SL-01), a content hash inside each file and a
`backups` subfolder (SL-02), `Superseded Saves` by name (REQ-014). What G3 had not decided
was how much of each record's shape is baseline, how records are identified, and how many
files the stored data is. Deferring would have left `store`'s CONTRACT session, the next
one, with no schema to write against.

## Decision
`baseline/schema.js` fixes: the data folder layout (`data.json`, `profiles.json`, `files/`,
`backups/`, `Superseded Saves/`); one envelope for every JSON file Pivot writes, carrying
the marker, the schema version, the write time in AEST, the save stamp, and the SHA-256 of
the canonical body; the header every stored record carries (id, kind, status, who created
and last changed it and when); and the body of `data.json` as one collection per record
kind plus the hazard sequence. The fields of each record kind beyond the header are
declared by the module that owns the kind, in its contract, so adding a field to a hazard
is an Interface change to `registry` and not a baseline change. All stored data is one
file, `data.json`, which is also the save-state and backup format (REQ-064). A hazard's
global ID is `H-` and a number from a sequence stored in the data that only counts up
(REQ-050); every other record has a random UUID. `store` alone reads and writes any of it.

## Alternatives considered
### Every record kind's full field list in `baseline/`
Rejected because: it designs the fields of eleven modules before their contracts exist,
which is the contract author's work (P10), and it makes every added field a baseline gate,
so the heaviest ceremony would fall on the most frequent change. The header is what crosses
modules (the change log reads it for every kind); the rest does not.

### One file per record, or per record kind
Rejected because: SL-02 promises a save that replaces stored data whole or not at all, and
SL-01's stamp tells one user's save from another's; both are one comparison and one write
when the data is one file, and a transaction across hundreds of files when it is not. The
integrity check per file (REQ-074) then covers the whole data in one hash.

### A UUID for hazards as for every other record
Rejected because: STK-028 asks for an ID a person reads in the hazard list, and REQ-050
asks that it never be reused, which a stored counter gives with one field. A UUID satisfies
the second and not the first.

### A sequence number for every record kind
Rejected because: every create by every user would then contend on one counter in a shared
folder, and only the hazard's ID is read by people (REQ-051 gives platforms their own).

## Consequences
- Makes easy: `store`'s contract, which sees only envelopes and the header; the change log
  and the reference register, which refer to any record by kind and id; an integrity check
  and a stamp comparison that are each one operation.
- Makes hard: partial saves of one record; data folders large enough that one file is slow
  to read, which DEC-003 already accepts; a record kind whose fields need to be read by a
  module other than its owner, which must go through the owner's contract.
- Locks in: the envelope and header shapes at schema version 1; `data.json` as the unit of
  save, backup, and restore; `H-nnnn` as the form of a hazard's global ID.

## Reversal
Cost to undo: days, plus a migration of every data folder in the old shape, under
CORE-CHG-002; the schema version in the envelope exists so that an old build refuses a
newer file rather than misreading it.
Would be triggered by: a data folder too large to save as one file within the time a user
will wait; a second module needing to read a record kind's fields directly; or slice 1
finding that the browser cannot write one file atomically enough for the stamp comparison
to hold.
