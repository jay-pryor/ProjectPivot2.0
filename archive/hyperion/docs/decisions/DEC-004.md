# DEC-004: Eleven modules over one store, decomposed by what changes together
Date: 2026-09-14
Status: accepted
Tier: baseline

## Context
G2 decomposes the 80 requirements into modules under the CORE-LFC-004 rules: a change to
one requirement touches one module, and two modules that always change together are one.
Three decompositions were seriously considered. The module dependency graph is baseline,
so the choice is recorded here rather than left to the module map alone.

## Decision
The decomposition in `docs/module-map.md`: one `store` module owning the data folder;
five record modules (`registry`, `reference-register`, `review-schedule`, `change-log`,
`profiles`) each owning one kind of record; two pure modules (`rating`, `bowtie`); two
composing modules (`workflows`, `reports`); and one screen module (`views`). The active
user is a baseline value passed into calls, so only `views` depends on `profiles`, and
`change-log` sits below `registry` and is keyed by platform, so no record module depends
on another and the graph has no cycle.

## Alternatives considered
### One data module holding every record kind
Rejected because: a change to the review tempo rules (STK-016) and a change to the
control library (STK-030) would both touch it, and its responsibility could not be
stated without a list; the largest slice of hazards (HZ-001, HZ-002, HZ-004 to HZ-007)
would all sit behind one contract, so every lens review would read the whole thing.

### Splitting `store` into persistence, backup, and concurrency modules
Rejected because: REQ-014, REQ-062, and REQ-074 are each a property of the one save path
(what is written, when a copy is kept, what check accompanies it); three modules would
change together on every change to the file format, which is the second CORE-LFC-004
rule. The "and" in `store`'s responsibility is justified here.

### Putting the change log inside `registry`
Rejected because: `reference-register`, `review-schedule`, and `workflows` also write
history (REQ-045 names every record kind), so a log inside `registry` would make every
other record module depend on `registry` or keep its own log; and STK-017's visible
history is one view, so one record.

### Giving `change-log` a dependency on `registry` to resolve platform owners
Rejected because: it creates a cycle (`registry` records its changes through
`change-log`). Keying acknowledgements by platform instead of by owner removes the need
and makes REQ-081 (transfer of ownership) fall out with no extra data.

### Making `rating` part of `baseline`
Rejected because: HZ-010's mitigation needs a contract clause and a conformance test,
and `baseline/` has neither; the matrix values are a module, the level and letter types
are baseline.

## Consequences
- Makes easy: reviewing each hazard behind one contract; stubbing any record module at
  its contract for a slice; replacing `views` wholesale, since nothing depends on it.
- Makes hard: any operation that spans record modules (REQ-026, REQ-068) must be composed
  in `views` or `workflows`, never by one record module reaching another.
- Locks in: `store` as the only module that touches the data folder; the direction of
  every edge in the module map.

## Reversal
Cost to undo: days per module moved (the contract, its suite, and every consumer the
manifests name), under CORE-CHG-002 because the graph is baseline.
Would be triggered by: slice 1 finding that `store` cannot be honest about REQ-014 without
knowing record kinds, which would pull it up into the record modules; or two record
modules found changing together across three consecutive slices.
