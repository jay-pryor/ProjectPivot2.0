# DEC-003: Pivot is one module per source file, built by a checked-in script into a single pivot.html, with no framework
Date: 2026-09-14
Status: accepted
Tier: baseline

## Context
G2 must record the tech stack before G3 writes contracts in a language. REQ-040 and
REQ-041 fix the runtime: a Chromium-based browser on a Windows machine with no
administrator rights and nothing installed. REQ-069 and ASM-004 fix the storage: one
shared data folder that every user reaches from their own machine. Every module's
language, test runner, and boundary check follow from this choice, and CORE-LFC-004 makes
third-party dependencies baseline, so the choice also decides how much substrate the
project carries. Deferring it would leave G3 writing contracts with no language to write
them in.

A page opened from a file path has a null origin in Chromium, and a module script it
imports from a second file fails the cross-origin check. A folder of separate module
files therefore does not run on the target machines without a local server or a browser
flag, and REQ-041 rules both out. Whatever is distributed must be one file.

## Decision
Each module is written as plain ES module JavaScript in its own source file under
`modules/<name>/src/`, with real import statements between modules. A small checked-in
script under `baseline/` reads every module, embeds each as an inline module in one HTML
file, and resolves the imports between them with an inline import map, so the built
`pivot.html` is self-contained and opens from the shared folder with no fetch of any
second file. The script is the whole build: no bundler, no third-party tool, no
dependency. There is no UI framework. Types are declared in JSDoc and checked by the
TypeScript compiler in CI only, so the type check, and IMP-05 with it, costs one
development dependency and no runtime one. Tests run under Node's built-in test runner
with its JUnit reporter against the source files, which is what `trace/results.xml`
needs. The data folder is reached through the browser's File System Access API, which
exists only in Chromium-based browsers, the same set ASM-001 already assumes. Module
boundaries are enforced by a small checked-in script over the real import statements
against the manifests, in the CI position `check_boundaries.py` would occupy, per
CORE-CON-003. The fault-point harness is a JavaScript equivalent of the framework's
`faults.py` template, written in the BASELINE session that instantiates `baseline/`.
`pivot.html` is generated, never committed; CI builds it and it is what a release ships.

## Alternatives considered
### A folder of separate module files opened directly, with no build
Rejected because: Chromium blocks the import of one file-path module from another, so
the page would not run on any target machine without a server or a flag; and a folder
of files gives every user a copy that can be partially updated.

### A third-party bundler (Vite, esbuild, Rollup)
Rejected because: the build needs only to inline a known list of files into one page,
which forty lines of checked-in script do; a bundler puts a compiler and its dependency
tree into the baseline for that, and its upgrade cadence into every slice.

### Concatenating the modules into one classic script, stripping imports and exports
Rejected because: the source files would no longer be the thing that runs; module
boundaries would exist in the source and vanish in the build, and a name clash between
two modules would be invisible until the build.

### A UI framework (React, Vue, Svelte)
Rejected because: Pivot's screens are lists, forms, and one diagram; a framework is a
large baseline dependency whose upgrade cadence the project would inherit, and it adds
nothing a requirement asks for.

### A desktop shell (Electron, Tauri)
Rejected because: it installs software, which REQ-041 forbids, and needs administrator
rights on a locked-down machine, which REQ-040 forbids.

### A local server (Python, Node) serving the page
Rejected because: it installs software (REQ-041), and a shared server would make the data
folder a service, changing ASM-004 and the storage topology G1 settled.

### Plain JavaScript with no type check
Rejected because: IMP-05 puts units and frames in type names, and a consequence level, a
likelihood letter, and an AEST date confused with each other is HZ-010 and HZ-012 by
another route; the type check is the compiler error P2 prefers.

## Consequences
- Makes easy: distribution (copy one file next to the data folder), running on any
  Chromium machine, reading and testing the code as separate modules, keeping the
  baseline's dependency list at one entry.
- Makes hard: any browser other than Chromium; large-file or many-user performance, since
  every read and write is a browser file operation; anything a library would have given
  for free (a diagram layout, a document exporter) must be written or added by an
  explicit IMP-06 instruction; a user running an old `pivot.html` against data written by
  a newer one, which the persisted schema in `baseline/` must version.
- Locks in: JavaScript as the contract language for every module; the File System Access
  API as the whole of `store`'s substrate; JSDoc as where types live; one built file as
  the only thing that runs.

## Reversal
Cost to undo: weeks (every contract and every module is in the language; the store
module is written against one browser API). Replacing the build script alone is hours,
since the source files are unchanged by it.
Would be triggered by: a target machine's browser policy blocking the File System Access
API from a page opened from the shared folder, which slice 1 exists to find out; a
decision to run Pivot on a non-Chromium browser; or Chromium withdrawing inline import
maps.
