# DEC-022: A file a record carries is stored as the user's own bytes, outside the envelope and integrity check
Date: 2026-09-16
Status: accepted
Tier: interface

## Context
SL-10 criterion 2 requires a reference register entry's file to be kept in the data folder
with only its location on the entry (REQ-029), and criterion 4 requires an entry whose file
cannot be found to be flagged wherever it is listed (REQ-078). Store 2.0 exposes no file
operation at all, and two of its clauses positively forbid one:

- C-009 confinement lists the files the module may touch, and `files/` is not among them,
  although `baseline/schema.js` has declared `DATA_FOLDER.files` since the baseline was
  instantiated.
- C-012 promises that **every** file the module writes to the folder is a sealed `schema`
  envelope carrying the integrity check of its body. A reference file is a PDF, an image, a
  spreadsheet — arbitrary bytes that are not JSON and cannot be an envelope.

So C-012 had to be resolved before an operation could be written, not after. Deferring it
would have meant writing an operation whose behaviour contradicted a standing clause.

## Decision
A stored file under `files/` is the user's own bytes, written and returned unchanged. It
carries no envelope, no header, and no integrity check; it is not a Pivot file name; and
`checkFolder` neither opens nor lists it. C-012 narrows to say so explicitly. The question a
stored file can be asked is presence, not integrity, and `checkStoredFiles` (C-019) answers
it as a value — `present: false` with a reason — never as a rejection, so a list can be
flagged row by row without a failure path per row.

C-009 widens to admit `files/`, written only by `putStoredFile` and only ever by creation:
no operation of this module replaces or removes a file there. `putStoredFile` (C-018) is
whole-or-not-at-all in the way C-010 makes `save` whole-or-not-at-all, and returns a
location that is fresh on every call, so two files of the same name cannot collide and no
record's location is disturbed by a later record.

## Alternatives considered
### Seal the user's file inside a `schema` envelope, like every other file Pivot writes
Rejected because it would take the user's file away from them. The whole point of one
chosen data folder (REQ-069) is that the user can open it; a PDF wrapped in JSON is a PDF
the user can no longer double-click, and Pivot offers no export path to get it back out.
It also doubles the folder's size for binary content through base64, for a check no
acceptance criterion asks for.

### Keep a hash of the file's bytes on the entry, so integrity is checkable without an envelope
Rejected because REQ-029 says the entry holds the file's location and nothing of its
contents, and a hash of the contents is contents. It would also make the location a
structured value rather than an opaque string, which is the one thing `reference-register`
asked not to have to know about. No criterion asks whether a stored file was altered — only
whether it can be found.

### Extend `checkFolder` to cover stored files, adding a fifth `AffectedData` value
Rejected because `checkFolder` is the pre-open sweep that tells the user what they cannot
rely on before anything is shown (SL-02 criterion 1), and it reads and hashes every file it
covers. Stored files are unbounded in number and size, so folding them in would make the
sweep cost grow with the user's attachments, and a missing attachment is not a reason to
hold back the whole folder. Presence belongs on the list that shows the entry, which is
where criterion 4 puts it.

### Give `putStoredFile` a delete, move, or rename alongside the write
Rejected because no SL-10 criterion asks for one and nothing in Pivot removes a record's
row (registry C-005, C-025). Retiring a reference entry is REQ-067's fourth kind, which
registry CONTRACT.md section 7 records as having no home and being a GATE decision. Adding
a removal now would be a promise made ahead of the decision that defines it.

## Consequences
- Makes easy: `reference-register` can hold a location as an opaque string and derive
  criterion 4's flag for a whole list in one call; a user can open their own files in the
  data folder with the program that made them.
- Makes hard: detecting that a stored file was altered or truncated after Pivot wrote it.
  C-019 will report such a file present. If that ever matters it is a new clause and a new
  decision, not a change to this one.
- Locks in: `files/` only grows. Until REQ-067's reference-entry half has a home, nothing
  removes a stored file, so the folder accumulates files whose records no longer name them.

**Open, and not settled by this record.** REQ-078 and SL-10 criterion 4 say "when an entry's
file **or path** cannot be found". A `path` is a filesystem path the user typed, on a machine
Pivot was never given a handle for; under DEC-003 a browser page cannot stat it. The file
half is answered by C-019. The path half has no mechanism in any module, and widening store
to invent one would be worse than leaving it open. What criterion 4 means for a path is a
GATE ruling on the slice — either the flag covers files only, or the criterion changes.
Store promises nothing about it (section *Explicitly not promised*).

## Reversal
Cost to undo: hours. Narrowing C-012 and widening C-009 are single clauses; `putStoredFile`
and `checkStoredFiles` have no implementation yet, so reversing before SL-10 is implemented
costs only this contract and its conformance suite. After stored files exist in a user's
folder it is effectively permanent: files already written as raw bytes cannot be retrofitted
into envelopes without rewriting every one of them and every location that names it.
Would be triggered by: a requirement that Pivot detect tampering with a carried file, or a
decision that Pivot must be able to remove one.
