# DEC-024: The platforms a reference entry's act reaches are the union over its links, and linking waits past them
Date: 2026-09-16
Status: accepted
Tier: interface

## Context
`reference-register` 1.0 requires an `EntryAct` on both of its changing operations, carrying
`affectedPlatformIds` — "the caller's statement, computed from `registry.platformsAffected`
over the records this entry is linked to". That module holds no link to a platform and imports
no module that does (reference-register C-007, DEC-020), so the list has to be derived by the
consumer. `views` is the only module that imports both `registry` and `reference-register`, so
at views 7.0 it is where the derivation lands, and it cannot be deferred: the field is required
and never defaulted, and `change-log` C-010 decides from it which platforms await the act.

Two things had to be settled before `createReference` and `linkReference` could be written.

First, `LINKABLE_KINDS` holds six kinds and `registry` owns five of them. A `report` ref is in
`LINKABLE_KINDS` because REQ-030 names it, but no module owns `report` until SL-09, and
`registry.platformsAffected` rejects a kind it does not own with `UnownedRecordKindError`
(registry C-024) rather than answering with an empty list. So a rule that passed every one of an
entry's links to `platformsAffected` would reject as soon as a user linked a reference to a
report.

Second, views C-027 promises that an edit reaching more than one platform is listed and
proceeded past before it is made, and at 6.0 that clause had six operations and no exception.
Linking a reference to a hazard that sits on four platforms changes what four platforms read.
Leaving it ungated would put the first exception into C-027.

## Decision
The platforms a reference entry's act reaches are the union of `registry.platformsAffected` over
the entry's own `links` as they will be after the act, each id once, ascending as strings. A ref
whose kind is `report` is not passed to `platformsAffected` and contributes nothing to the union;
every other kind of `LINKABLE_KINDS` is one `registry` owns and is passed. A new entry has no
links, so `createReference` always derives an empty list and reaches no platform.

`linkReference` is C-027's seventh gate, on that same union: two or more ids and the act waits on
the confirm-edit screen past the list of them, exactly as the six before it. `createReference` is
never gated, because an entry with no links reaches nothing.

## Alternatives considered
### Pass an empty `affectedPlatformIds` for every reference entry act
Rejected because it makes the register invisible to the people REQ-012 exists for. A reference is
kept against a hazard so that the platforms carrying that hazard have it; an owner who is never
told the reference changed is an owner reading a register they cannot trust. The field would
also be a statement this module knows to be false, which `reference-register`'s not-promised
section warns is uncheckable from there — "an act recorded with a platform missing from that list
never reaches that platform's queue, and this module cannot tell".

### Derive the union from the one ref being linked rather than from the whole entry
Rejected because the record that changed is the entry, not the ref. An entry already linked to a
hazard on P1 and P2, linked now to a control on P3, is an entry P1 and P2 read and whose content
just changed; warning only about P3 would tell the user less than the act does. It would also
break the identity C-027 rests on, that what the user was warned about is what then awaits
acknowledgement, because the entry `reference-register` C-011 writes carries the act's own list.

### Widen `registry.platformsAffected` to answer for a `report` with an empty list
Rejected because registry C-024 refuses an unowned kind deliberately: "an empty list would be
this module claiming a change reaches nowhere when it holds no link to say so". Turning that
refusal into a silent empty answer would remove the one signal that a kind has found an owner,
and would have to be undone at SL-09 when a module owns `report`. Skipping the ref in `views`
keeps the refusal and puts the gap where it can be seen.

### Leave `linkReference` ungated, since REQ-011's words do not reach it
Rejected on the same ground DEC-021 took for `setReviewTempo`: REQ-011 names a hazard, a control,
or a justification, and a reference entry is none of them, but where a fact is stored should not
decide what a user is told before changing it. A reference linked to a hazard is content the
hazard's platforms read, and a clause with one exception is a clause every later version has to
re-argue. Recorded as a promise beyond the requirement, as DEC-021 was.

## Consequences
- Makes easy: an owner is told when a reference their platforms read gains a link; C-027 keeps a
  single rule over seven operations; `reference-register` stays free of any knowledge of a
  platform.
- Makes hard: a reference linked to many records costs one `registry.platformsAffected` per link
  of an owned kind before the act, which is the only place in `views` where a read is repeated
  per link. Linking to a reference-heavy hazard is slower than linking a control to a hazard.
- Locks in: a `report` link reaching no platform. Until a module owns `report`, a reference linked
  only to reports is an act nobody awaits, and a user is warned about nothing before making it.

## Reversal
Cost to undo: hours. The union is one clause of `views` and one paragraph of C-027; nothing is
stored differently, because `affectedPlatformIds` lives on a `change-log` entry whose shape is
unchanged. Reversing after entries have been acknowledged leaves past entries carrying the union
and later ones carrying whatever replaces it, which is history and not a migration.
Would be triggered by: a module owning `report` at SL-09, which makes the skipped ref answerable
and is the moment to revisit the union; or a ruling that a reference entry is not content a
platform reads, which would take `linkReference` back out of C-027.
