# DEC-010: Browser drivers are development aids outside the repository, never a dependency of Pivot or its suites
Date: 2026-09-15
Status: accepted
Tier: interface

## Context
DEC-007 rejected running the `views` conformance suite in Chromium through Playwright or
Puppeteer, and its wording has been read as forbidding browser drivers altogether. What it
rejected was a dependency and a second test runner, not a session looking at the page. An
IMPLEMENT session drawing a `Screen` into DOM has no way to see what it drew, so the
drawing's defects surface only at the hands-on demonstration. A QUERY session confirmed
that the scope hook allows an IMPLEMENT session to run a program installed outside the
repository, and never sees the `claude-in-chrome` tools. Left unrecorded, a session either
avoids a useful aid because of DEC-007, or installs one into the project, which IMP-06
forbids. This record replaces DEC-007, restating its decision unchanged and making the
line on browser drivers exact.

## Decision
The `views` decision of DEC-007 stands unchanged: `modules/views/contract.js` promises a
`Screen`, plain data describing what the page shows, and one operation per user action,
each resolving with the next `Screen` and belonging to one screen kind. The conformance
suite drives these against the real `store`, `profiles`, and `registry` on `store`'s
in-memory folder under Node's test runner (DEC-003). Turning a `Screen` into DOM is the
implementation's, entered from `modules/views/src/main.js`, verified by demonstration and
recorded as review rows (REQ-057 and the criterion 1 row), never by a conformance test.

A browser driver (Playwright, Puppeteer, `claude-in-chrome`, or the installed Chromium
driven by hand) may be used by an IMPLEMENT session as a development aid, to open the built
page, read its console, and look at what was drawn, provided all of the following hold:
- it is installed by the human outside the repository, or is a tool of the runtime, never
  by the session;
- it appears in no file under version control: not `package.json`, not the lockfile, not
  `modules/**`, `integration/**`, `validation/**`, or `fixtures/**`;
- any script that drives it lives in the session's scratchpad, outside the repository;
- the test command, CI, and `trace/results.xml` neither run nor require it.

What such a session sees is not evidence. It verifies nothing a trace row can cite; the
demonstration rows remain a human on a target machine.

## Alternatives considered
### Keep DEC-007's wording
Rejected because: it reads as a ban on any browser driver, so an IMPLEMENT session draws
the page blind, while the reasons DEC-007 gave (a dependency, a browser the CI container
does not carry, a second runner splitting the results) concern only the suite.

### Browser drivers as a development dependency in `package.json`
Rejected because: a lockfile entry is a baseline change (CORE-CHG-002) and IMP-06 forbids a
dependency without an instruction; once present, a test under `modules/*/tests/` can import
it, and the suite then fails in the CI container without it.

### Running the conformance suite in Chromium
Rejected because: the reasons in DEC-007 stand. A browser driver is a dependency and a
browser install the CI container does not carry; the test command and `trace/results.xml`
are Node's runner (DEC-003), and a second runner would split the results the trace checker
reads; and a browser suite would spend its slow, flaky half on lists and forms, not on the
one browser risk.

### A simulated DOM as a development dependency (jsdom, happy-dom)
Rejected because: the reasons in DEC-007 stand. IMP-06 forbids it without an instruction,
and passing in jsdom says nothing about the File System Access API under the target
machines' policy, which is the risk criterion 1 exists to test.

### A mount-only contract, `mount(container)`, with the suite reading the drawn DOM
Rejected because: the reasons in DEC-007 stand. It needs a DOM in Node, and a suite that
asserts on elements asserts on the drawing, so a redraw would fail conformance
(CORE-CON-002).

### No conformance suite for views: every criterion by demonstration
Rejected because: the reasons in DEC-007 stand. Criteria 2, 5, and 6 are exact behaviours a
test checks on every change; HZ-008's "telling" half would have no named, passing test to
cite; and the null-double check (CORE-TST-002) needs a suite to fail.

## Consequences
- Makes easy: everything DEC-007 made easy; an IMPLEMENT session catching a broken drawing
  or a console error before the hands-on demonstration rather than at it.
- Makes hard: nothing a session sees in a browser can be cited, so the demonstration rows
  and targeted reads stay with the human; a driver script cannot be kept between sessions
  except outside the repository.
- Locks in: everything DEC-007 locked in; the rule that no browser driver appears in a
  versioned file or in the test command.
- Relies on: the scope hook denying a session's install into the project, and review of the
  diff for any versioned reference to a driver. The hook does not check where a program
  lives; that gap is upstream in `hyperion/`, not closed here.

## Reversal
Cost to undo: hours for the browser-driver clause, which leaves nothing in the repository
to remove; the `views` decision's cost is as DEC-007 recorded it.
Would be triggered by: a driver reference appearing in a versioned file or the test command
despite this record, at which point the clause is withdrawn; or the triggers DEC-007
recorded for the `views` decision.
