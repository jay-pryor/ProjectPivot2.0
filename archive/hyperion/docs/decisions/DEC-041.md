# DEC-041: A stand-in stub is a minimal honest implementation that passes the whole suite; only the null double is fixed data
Date: 2026-09-23
Status: accepted
Tier: internal

## Context
CORE-LFC-005's stub policy holds an OPEN question for the human: a stand-in stub "returns fixed
valid data" and "must pass the suite", but a null double is also fixed valid data and the suite
must fail against it (CORE-TST-002 rung 1). The two cannot both hold, so either a stub is a
minimal honest implementation, or it passes only the files the slice exercises. G3 cannot be
reviewed without the ruling, because the null-double criterion and the slice loop's stub rule
read the same suite in opposite directions, and every Pivot suite imports other modules through
their contracts, so the first IMPLEMENT session will need stand-ins for what it does not build.
jay-pryor ruled at the G3 gate review (REV-005).

## Decision
A stand-in stub for an unbuilt module is a minimal honest implementation: the smallest
`modules/<m>/src/` that passes that module's whole conformance suite, not only the files the
slice exercises. It may return fixed data only where the contract permits a constant answer.
It is written by an IMPLEMENT session in the slice that first needs the unbuilt module, and is
replaced in place when that module's own slice builds it. It is never the null double and never
contains null-double code. The null double, written at CONTRACT (DEC-039), is the only
fixed-data implementation a module has, and the suite must fail against it in every one of
`test_errors`, `test_invariants`, and `test_boundaries`. Decided by jay-pryor.

## Alternatives considered
### A fixed-data stub that passes only the conformance files the slice exercises
Rejected because: Pivot's hazards are about data correctness, and a partly-checked stand-in is
where a wrong assumption slips through to the module that depends on it. Also, which files a
slice "exercises" is a judgement no check can make, so the rule would be honour-based (P2).

## Consequences
- Makes easy: `check_null_doubles.py` and the stub rule reading the suite the same way; a
  consumer slice trusting a stand-in as far as it trusts the contract.
- Makes hard: the first slice that needs a stand-in pays for a working implementation of it,
  which is the cost the honest reading always had. In Pivot the record modules are small
  functions of a body, so the cost is bounded.
- Locks in: no `modules/*/src/` that fails its own suite, ever, stub or not.

## Reversal
Cost to undo: hours. Nothing is stored; the rule is what an IMPLEMENT session may write.
Would be triggered by: a stand-in found to cost as much as the module it stands in for, across
more than one slice, which would reopen the question upstream in `hyperion/`.
