# DEC-017: The platforms an edit reaches are listed before the edit is made, not at the save; the queue is every platform the active profile owns; the history is one screen
Date: 2026-09-16
Status: accepted
Tier: interface

## Context
`change-log` 1.0 (DEC-015) and `registry` 4.0 (DEC-016) settled where an entry comes from and
what it holds. Three of SL-05's six criteria are `views`', and none of them can be written
without answering questions the other two sessions deliberately left here.

Criterion 3 says Pivot "lists every platform the edit changes and requires the user to proceed
past that list" **before saving** an edit that reaches more than one platform. In Pivot an edit
reaches the working body when the operation is called, is mirrored and backed up at once
(store C-013, views C-012), and reaches the folder at `save`. "Before saving" therefore names
two different moments, and the registry act — with its entry and its queue — happens at the
first of them.

Criterion 4 says each other affected platform's owner sees "the change and every item it
affects". `change-log` read that as every record the one act changed, which is what an entry
holds, and recorded that the other reading — every item of that platform the changed records
appear in, the hazard's row and its controls — is a composition of `registry`'s per-platform
query with those entries, "not refused but placed" at this session.

Criteria 1 and 2 ask that the history be viewable by any user. `change-log` gives three reads:
the whole log, one record's history, and one platform's queue. Which of them a screen is built
from, and how many screens there are, is this session's.

## Decision
**The list comes before the edit, not before the save.** Five operations can change a record
more than one platform reads — `renameHazard`, `addCausalFactor`, `addConsequence`, and
`linkControlToHazard` on the hazard screen, and `retireControl` on the controls screen. Each
calls `registry.platformsAffected` first, and when that gives two or more platforms it resolves
with a confirm-edit screen listing them and changes nothing: no registry call, no entry, no
`noteChange`, nothing in the folder or the browser. `confirmEdit` makes the call the operation
would have made; `cancelEdit` leaves with nothing done. No other operation is offered on that
screen, so the list is the only way through (views C-027).

**One derivation, not two.** The platforms listed come from `registry.platformsAffected`, the
same function whose result `registry` C-023 gives the entry as its `affectedPlatformIds`. None
of the five changes a `hazard-platform` link, so the list before the act and the list on the
entry are the same list: what a user was warned about is exactly what then awaits
acknowledgement.

**The queue is every platform the active profile owns.** `openAcknowledgements` lists one queue
per platform whose `ownerProfileId` is the active profile's, each from one
`change-log.listAwaiting`; `acknowledgeChange` is offered only for a row the screen shows, which
is this module's half of who may acknowledge. "Every item it affects" is the entry's own items,
`change-log`'s reading; the composition with `listPlatformHazards` is not built at 5.0.

**The history is one screen, the whole log.** `openHistory` shows `change-log.listEntries` of
the working body, every act of both entry kinds, unfiltered and ungrouped, with the profiles
an entry's `createdBy` is drawn with. `listHistory` is not called at 5.0.

**Retirement is three operations that take a thing off no platform.** `retireHazard` on the
hazard screen (leaving it, with the refusal naming the platforms when the hazard is on any),
`retireControl` and `retirePlatform` on their lists; and `setPlatformOwner` on the platforms
screen is what carries a queue across (views C-030, C-018).

## Alternatives considered
### The list at `save`, naming every platform every unsaved change reaches
Rejected because: by then the acts are made, the entries are written, and the platforms already
await them — so "requires the user to proceed past that list" would gate nothing that could
still be stopped, and declining would need an undo this version does not have (registry's
not-promised section). It also loses the attribution: one list for many edits cannot say which
edit reached which platform, and the criterion is about an edit, singular.

### Warning both before the edit and again at the save
Rejected because: the second warning is the first one repeated with nothing the user can do
about it, and a warning that cannot be acted on trains the user past the one that can.

### `views` computing the affected platforms itself, from the links
Rejected because: it would be a second derivation of the one thing criteria 3 and 4 must agree
on, and DEC-016 made `platformsAffected` the single definition for exactly that reason. It also
needs `views` to read `collections.link`, which C-009's confinement forbids.

### Gating on the hazard's platform count rather than on `platformsAffected`
Rejected because: it is the same number today and a guess tomorrow. A causal factor's platforms
are its hazard's *because registry C-024 says so*; asking `platformsAffected` is asking the
module that owns the links, and the answer changes with the links rather than with a rule
written here.

### Validating the title or text before showing the list
Rejected because: `views` would need `registry`'s blankness and trimming rules to do it, which
C-009 forbids and which would drift. The cost is that a blank title is refused after the list
rather than before it — one extra step in a case the user is already fixing.

### Acknowledging from a dashboard, or from the platform's own screen
Rejected because: the queue is keyed by platform and read per platform, so one screen per owner
showing all of their platforms is one read per owned platform and one place to look. The
platform screen is reached from the platforms list and is about that platform's hazards; the
dashboard is SL-11's (REQ-066, REQ-068).

### Showing, beside each awaiting entry, the platform's rows for the records it changed
Rejected because: it is the second reading of criterion 4's "every item it affects", and the
entry already holds every record the act changed with each field's previous and new value —
which is what the owner needs to judge it. The composition costs one per-platform query per
entry, is a list view of the kind REQ-026 and SL-11 own, and would put a derived list beside an
entry that is a record of fact.

### A per-record history screen, from `change-log.listHistory`
Rejected because: criteria 1 and 2 ask for a history viewable by any user, not for one per
record, and a second entry point into a history screen would make `back` ambiguous — the
navigation model holds one edge per screen kind (views C-015). The whole log answers "what
happened to this record" by containing it; a per-record view is a later version.

### A queue for retired platforms as well
Rejected because: `registry` 4.0 lists live platforms only and has no read for a retired one, so
this would need an Interface change to `registry` for a platform out of use. The consequence is
recorded rather than hidden: a retired platform's entries stay awaiting and are shown to nobody
until a later version lists them.

## Consequences
- Makes easy: stopping an edit that would reach platforms the user had not thought about, at
  the moment they can still abandon it; one place to read what happened; one screen per owner
  for what they have not acknowledged; a transfer of ownership that carries the queue with no
  data of its own (`change-log` C-012).
- Makes hard: editing a hazard that is on many platforms without seeing them; telling the user
  a title is blank before showing the list; finding the history of one record among all of
  them; showing a retired platform's queue or its name.
- Locks in: the confirm-edit screen as the shape of every "before you save this" gate a later
  slice adds; `platformsAffected` as the only source of an affected platform in this module;
  `Platform.ownerProfileId` as the one thing that decides whose queue is shown, so entitlement
  to acknowledge is never stored on an entry.

## Reversal
Cost to undo: hours while no implementation exists. Days afterwards for the gate, because five
operations and one screen kind carry it; hours for the history screen, which is one read
swapped for another. The entries are unaffected either way: nothing here changes what
`change-log` stores.
Would be triggered by: a user finding the list shown too often to read — which would move the
gate to the save and accept that it only informs — or a folder whose history grows past what
one screen can show, which is DEC-003's reversal trigger arriving through the log
(`change-log` section 6) and would force filtering or a per-record view.
