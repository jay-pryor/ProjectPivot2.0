# DEC-030: An export is written through store, by an operation that writes given text to a file the user chose, not by the page
Date: 2026-09-16
Status: proposed
Tier: interface

## Context
SL-08 criterion 3 says exporting writes the bow-tie diagram to a file the user chooses, and the
exported drawing holds the same nodes as the shown one. No contract allowed that write. `store`
3.0 C-009 confines the module to the data folder and the one browser storage key;
`chooseSaveStateFile` only reads; and `views` C-009 sends every write through `store`. The
bowtie 1.0 preamble names the gap. Deferring it leaves criterion 3 with no operation to verify,
and SL-08 cannot be implemented within existing contracts.

jay-pryor chose to put the write in `store`, so that criterion 3's write can be tested.

## Decision
`store` 4.0 adds two operations. `chooseExportFile(suggestedName)` shows the browser's save file
picker and resolves with an `ExportFileHandle`; it talks to the browser and is verified by
demonstration. `writeExportFile(target, text)` writes the text to that handle whole or not at all
(C-020), and is reached by the conformance suite through an in-memory handle, the way
`openDataFolder` takes an in-memory folder. C-009 widens to that one file and nothing more:
nothing under the data folder, not the browser's storage, and nothing kept, mirrored, or backed
up. The write takes text, not a bow-tie, so `store` knows nothing of `bowtie`, and it takes no
`DataStore` or profile, because it replaces no stored data.

## Alternatives considered
### The page (`src/main.js`) writes the file itself with `showSaveFilePicker`
Rejected because the write would sit outside every contract, so no conformance test could reach
it. Criterion 3's "writes the diagram to a file" would be verified only by hand, and nothing would
stop the page's write from drifting from C-009's confinement or from DEC-004's rule that the
folder and the browser's files are reached only through `store`. It would also make `views` C-009
false, or require a second exception there, for a write the page would still have to get right
with no test to hold it.

### A bow-tie-specific operation, `exportBowtie(bowtie)`, in `store`
Rejected because it would make `store` import `bowtie` for a write that needs only a string. That
adds a manifest edge for no promise, and SL-09's reports, which also need to leave Pivot as a file,
would each need an operation of their own.

### Take a `DataStore` and an active profile, like `putStoredFile`
Rejected because both exist to protect stored data. C-002's reason is data put into the folder and
C-003's is overwriting another copy's save, and the export does neither. Requiring them would make
the export fail for reasons that have nothing to do with it.

## Consequences
- Makes easy: a conformance test for criterion 3's write, with no browser, including what an
  interrupted write leaves (fault point `store.export.staged`); reuse for any later export of text.
- Makes hard: nothing checks that the text is the drawing shown. That stays the caller passing
  the same `BowtieSvgText` to both, `views`' half of criterion 3.
- Locks in: C-009's confinement now has one exception outside the folder. A later export of
  binary content (PNG was rejected at G3) would need a second operation or a widened one.

## Reversal
Cost to undo: hours. Remove two operations, C-020, and a C-009 sentence, then run the Interface
sequence. Nothing persisted depends on it.
Would be triggered by: a target browser without `showSaveFilePicker` (DEC-003's reversal
trigger), or a ruling that exports belong to a module of their own.
