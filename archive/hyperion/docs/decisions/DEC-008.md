# DEC-008: A backup holds the working state and is taken on a change once an hour has passed since the newest one
Date: 2026-09-15
Status: accepted
Tier: interface

## Context
The `store` CONTRACT session for SL-02 found criterion 3 readable three ways: a backup taken
inside a save, one taken on the next edit, or one taken the moment the hour elapses (REQ-062
says "immediately"; ASM-003 implies a check on opening). What the backup holds was also
open. Each reading gives `store` a different operation and a different ring. jay-pryor ruled
in the session: any edit to the working state, saved or not, together with more than an hour
since the last backup, and the backup holds the working state. Deferring would have left
the conformance suite for criterion 3 with nothing falsifiable to test.

## Decision
The consumer tells `store` of every change to the working state through `noteChange`. When
the body differs from the one the store last held and the newest backup in `backups/` (by
the time in its name, across every copy of Pivot on the folder) is more than an hour old,
or there is none, `store` writes the changed working state as a sealed `data` envelope with
a fresh stamp under `backups/`, then prunes the ring to 72, oldest first. No other operation
writes a backup (store C-013, C-014).

## Alternatives considered
### A copy of `data.json` as last saved, taken on a change
Rejected because: unsaved edits would write copies of the same saved file hour after hour,
and 72 identical copies push older distinct backups out of the ring, so the ring would
protect less the longer a user worked without saving.

### A backup taken inside `save`
Rejected because: edits a user never saves are never backed up, which leaves the crash and
the forgotten save uncovered, and it is the reading the ruling set aside.

### A timer that backs up when the hour elapses
Rejected because: it needs a clock loop inside a module whose every other operation is a
call, the suite would have to drive time rather than fix it, and a backup with no change
since the last one is the duplicate the first alternative produces.

## Consequences
- Makes easy: a restore that brings back work nobody saved; a criterion 3 test that fixes
  the clock, calls `noteChange`, and counts files.
- Makes hard: a backup no longer means "what was in the folder"; it may hold changes that
  were never saved and that another user's later save would have superseded. Restore still
  goes through `save` (C-017), so C-004 keeps whatever it replaces from another user.
- Locks in: `noteChange` as the consumer's duty on every change (views, then workflows);
  REQ-062's wording ("stored data has changed", "a backup of the stored data") now lags
  this ruling and needs rewording at a GATE session.

## Reversal
Cost to undo: hours. Backups written either way are the same `data.json` format (REQ-064),
so existing rings stay restorable; only `store`'s C-013 and its suite change.
Would be triggered by: a ring found full of backups of abandoned edits when a user needs an
older saved state, or `noteChange` found too slow on a large body.
