# DEC-016: The module that owns a record writes its own history — every changing operation takes an act, appends the entry to the body it returns, and derives the platforms the act reaches from its own links
Date: 2026-09-16
Status: accepted
Tier: interface

## Context
DEC-015 fixed the shape of a change-log entry and left two of its fields to the caller:
`madeForPlatformId`, the platform an act was made for, and `affectedPlatformIds`, every
platform it reaches. It named `registry` as that caller, because the links an act reaches are
`registry`'s and a `change-log` that asked would close the cycle DEC-004 rejected. What it did
not settle is where the call is made from, and SL-05's `registry` CONTRACT session cannot be
written without it: criteria 1 and 2 ask that every create, edit, and deletion of a stored
record keep an entry, and the record kinds SL-03 and SL-04 store are all `registry`'s.

Three questions force it now. Where the `change-log.recordChange` call is made: inside the
operation that changed the record, or in the consumer afterwards. How the platform an act was
made for reaches the operation, given that every changing signature on this surface takes a
profile and nothing else. And what happens when an act changes nothing, because `change-log`
refuses a `before` deep-equal to its `after` (`UnchangedRecordError`), and two calls in the
same second with the same values produce exactly that.

## Decision
`registry` imports `modules/change-log/contract` and records its own acts. Every changing
operation appends the entry to the body it resolves with, in the same call: there is no
operation that writes a record and no entry, and a rejection from `change-log` rejects the
operation with nothing written, so a record and its history are stored together or not at all.

The second argument of every changing operation becomes an `Act` — `{ profile,
madeForPlatformId }` — in place of the bare `ActiveProfile`, which is DEC-015's unit of
history made the unit of the call. `madeForPlatformId` must be present and must be null or a
platform the body holds; it is not defaulted.

The platforms an act reaches are one derivation, `platformsAffected(body, ref)`, from the live
links this module holds. It is both what the entry carries and what `views` shows the user
before saving (SL-05 criterion 3), so the platforms a user was warned about and the platforms
that queue the change cannot differ.

An act that would change nothing is refused with `NoChangeError` rather than logged: a title,
report ID, owner, or pair of rating values equal to what is stored.

## Alternatives considered
### The consumer calls `change-log` after each `registry` call
Rejected because: a consumer that omits the call writes a record with no history, which is
HZ-005 exactly, and no test of either module can see the omission — the hole is in neither
diff. It also puts the before-and-after diff in the module that does not hold the "before":
`views` would have to keep a copy of each record across the call, and a stale copy is a wrong
history rather than a missing one.

### `registry` returns a `RecordedChange` for the consumer to pass on
Rejected because: it is the same hole one step later — the caller may still drop the value —
and it makes the act boundary the consumer's. An exclusion writes a justification and
supersedes a `control-platform` link in one call (C-021); if the consumer assembles the act,
two calls where DEC-015 wants one are a caller's mistake rather than an unreachable state.

### Keep `profile` and add `madeForPlatformId` as a further argument
Rejected because: the argument easiest to omit would be the one that decides whose queue the
change lands in, and its position would differ between operations that take an id and those
that do not. Folding it into one bundle with the profile makes an act one value, checked once,
and makes a caller that has not thought about the platform fail rather than default.

### Default a missing `madeForPlatformId` to null
Rejected because: null means "made for no platform", which queues the act on every platform it
reaches including the one the user is working on. It fails safe in the sense that nobody is
hidden from, but it fills the working platform's own queue with its owner's own edits, and a
queue that is mostly noise is not read — which is HZ-006 arriving by a longer road.

### `change-log` deriving the affected platforms itself
Rejected by DEC-015, for the cycle; restated here because this decision is what makes the
derivation `registry`'s in code as well as on paper.

### An act that changes nothing resolving quietly, writing neither record nor entry
Rejected because: a changing operation that sometimes does not change is harder to test than
one that refuses, and every other refusal on this surface is explicit — a blank title, a
duplicate link, a control already excluded. Refusing also names the condition where the user
can see it, rather than showing a save that appears to have worked and left no history.

## Consequences
- Makes easy: a history that cannot be skipped, because skipping it means not writing the
  record; one derivation behind the before-save list and the queue, so criteria 3 and 4 cannot
  disagree; an act that changes two records recorded as one entry with no work from the
  consumer.
- Makes hard: calling a changing operation without deciding which platform the user is on;
  recording a change made outside this module's operations, which is now the only way to write
  a `registry` record with no entry and is not reachable through the contract; re-titling a
  record to the value it already has.
- Locks in: the `Act` as the second argument of every changing operation on this surface;
  `registry` → `change-log` as an edge in the dependency graph; `platformsAffected` as the
  single definition of which platforms a change reaches, which every later module owning a
  record kind must supply for itself.

## Reversal
Cost to undo: hours while no implementation exists; days once one does, because every changing
signature and every consumer call site carries the `Act`. The entries already written would
remain valid — the shape is DEC-015's and does not change — so the data would survive a move
of the call site to the consumer.
Would be triggered by: a second consumer needing to record an act over `registry` records that
this module's operations cannot express, or a record kind whose owning module cannot compute
the platforms its changes reach, which would put the derivation back in the consumer.
