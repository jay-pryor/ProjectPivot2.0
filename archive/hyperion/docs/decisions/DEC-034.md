# DEC-034: produceReport refuses unless it is handed exactly the out-of-date list, and a report at 1.0 includes no reference entry
Date: 2026-09-16
Status: proposed
Tier: interface

## Context
HZ-009: "Pivot must never produce a report from out-of-date data without telling the user that the
data is out of date". REQ-016 and SL-09 criterion 3 require a warning, with each record's last
reviewed date, before producing a report that uses a hazard, control, platform, or reference entry
past its review due date, and no warning otherwise. `review-schedule` C-009 makes "past due" a fact.
What remained open was where the telling is enforced and which records a report uses. Criterion 3
names reference entries, but criterion 2's list of what a report holds does not.

## Decision
`reports.outOfDateFor(body, platformId)` gives every record a report on that platform would use (the
platform, each hazard row, each control of those rows) that `review-schedule.listOverdue` flags, in
its order, with name, due date, and last reviewed date. `produceReport` calls it and refuses with
`OutOfDateNotAcknowledgedError` unless `fields.acknowledgedOutOfDate` is exactly those refs in that
order. The report stores the list and both documents draw it (`reports` C-006, C-008). `views` shows
the list as a warning on the prepare-report screen exactly when it is not empty, and passes back the
refs it showed and nothing else (views C-042). A report at `reports` 1.0 includes no reference entry,
so none can make it out of date.

## Alternatives considered
### The warning in `views` alone, as the confirm-edit gate (views C-027)
Rejected because nothing in `reports` would stop a caller producing a report without the warning,
and HZ-009 would rest on one screen remembering to ask (P2). It would also let a list go stale
between showing it and producing (a due date crossed at midnight) without anyone noticing.

### A boolean `userWasWarned` on `ReportFields`
Rejected because a caller could pass `true` without showing anything, and a stale list would pass.

### Include the reference entries linked to the platform, hazards, or controls
Rejected for 1.0 because criterion 2 lists what a report holds and names none. Adding them would add
a dependency on `reference-register` and content no criterion asks for. Data a report does not hold
can't make it out of date, so HZ-009 is not weakened. The check is over what a report includes, so
including entries later brings them under the warning without changing the check. This is recorded
in `reports`' preamble for jay-pryor's review of criterion 3.

## Consequences
- Makes easy: a conformance test of HZ-009's telling in `reports` alone, including the stale-list
  refusal with the clock fixed either side of a due date.
- Makes hard: the out-of-date list can't be skipped, so a user who produces reports in bulk goes
  through the list each time.
- Locks in: `acknowledgedOutOfDate` on `ReportFields` and `outOfDate` on the stored report.

## Reversal
Cost to undo: hours for the refusal; the stored `outOfDate` field is persisted data (DEC-032).
Would be triggered by: a ruling that a report includes reference entries (a new `reports` version
imports `reference-register`), or a GATE ruling that moves HZ-009's mitigation to `reports` C-006.
