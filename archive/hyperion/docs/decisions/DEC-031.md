# DEC-031: The bow-tie is shown on a screen of its own reached from the assessment screen, and an export generates it again rather than writing the screen's copy
Date: 2026-09-16
Status: proposed
Tier: interface

## Context
SL-08 needs `views` to show the bow-tie of one hazard on one platform and to export it (criteria 1
to 3). `bowtie` 1.0 gives the value and the SVG document (DEC-028), and `store` 4.0 gives the write
to a file the user chooses (DEC-030). Two questions were left to the `views` 9.0 CONTRACT session.
Neither `bowtie` nor `store` could answer them, and no operation could be written without them.
First, which screen the bow-tie is reached from. Second, whether an export writes the drawing the
screen already carries or generates it again. REQ-059 says a bow-tie is generated "each time it is
shown, exported, or included in a report", and criterion 3 says the exported drawing holds the same
nodes as the shown one.

## Decision
The bow-tie has a screen of its own, reached by `openBowtie(app)` from the assessment screen, which
already holds the hazard and platform pair, and `back` returns to that assessment screen (C-015,
C-039). `exportBowtie(app, target)` calls `bowtie.bowtieFor` and `bowtie.renderBowtieSvg` again
on the working body and writes the text they give through `store.writeExportFile`. It then
resolves with the bow-tie screen built from those same results, so the screen's `svg` is the text
written (C-040). The two drawings are the same because nothing offered on the bow-tie screen
changes the working body and `bowtie` C-010 gives one document for one value. An export is not a
change: it isn't told to `store`, gated, or recorded.

## Alternatives considered
### Export writes the `svg` the bow-tie screen already carries
Rejected because the screen's `svg` would then be a copy of a bow-tie that a later act writes out,
which is the stored copy REQ-059 rules out, just held in memory instead of in the folder. It would
also make "each time it is exported" untrue. It would save only one pair of pure calls, and C-010
already makes the two texts identical.

### Reach the bow-tie from the hazard's own screen, with a platform chosen there
Rejected because the hazard screen holds no platform, and it is not specific to one. The operation
would need a `platformId` beside the hazard. That breaks the naming rule every operation since 3.0
keeps (section 2: never a `hazardId` and a `platformId` together). It would also need a second list
of the hazard's platforms, which is REQ-026 at SL-09.

### Export straight from the assessment screen, with no bow-tie screen
Rejected because criterion 3 compares the exported drawing with the shown one, and criterion 1
needs a shown drawing. A screen that carries the `svg` gives the conformance suite one value to
compare the file against, and gives the page one value to draw.

## Consequences
- Makes easy: criterion 3 is checked by one comparison, the in-memory target's contents against
  the screen's `svg`. Criterion 2 is checked by `openBowtie` after an edit, with the folder and
  browser storage compared before and after.
- Makes hard: an export costs the bow-tie's reads a second time (section 6), which is negligible
  at DEC-003's scale.
- Locks in: the bow-tie screen offers no changing operation. Adding one would break C-040's
  argument that the shown and exported drawings are the same, and would need the export to write
  the screen's text or refuse after a change.

## Reversal
Cost to undo: hours. It changes C-015's edge and C-040's calls, then runs the Interface sequence.
Nothing persisted depends on it.
Would be triggered by: a ruling that a bow-tie is reached from the hazard or platform screen or from
a report view (SL-09), or an act offered on the bow-tie screen itself.
