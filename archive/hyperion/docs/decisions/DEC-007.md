# DEC-007: The views contract is the screen as data; drawing it is internal and verified by demonstration
Date: 2026-09-15
Status: superseded by DEC-010
Tier: interface

## Context
The `views` CONTRACT session (SL-01) had to decide what the one screen module promises,
given that its conformance suite runs under Node's test runner with no browser and no
dependency (DEC-003, IMP-06). Node has no DOM, so a contract whose surface is "mount into
this element" has no suite that can run in CI, and SL-01 criteria 2, 5, and 6 (nothing
offered before a profile is selected; the saving user told of a supersession; no message
when there was none) would be verified by hand or not at all. Criteria 1 and 3 are
demonstrations on a target machine whatever is decided. Deferring would have left the
walking skeleton's last contract with no testable half, and every later screen slice
copying whatever `views` 1.0 did unrecorded.

## Decision
`modules/views/contract.js` promises a `Screen`, plain data describing what the page
shows (which of the three screens, the top bar's folder and profile names, the profiles
or hazards listed, whether there is unsaved work, the messages the last operation had to
say), and one operation per thing the user can do, each resolving with the next `Screen`.
The conformance suite drives these operations against the real `store`, `profiles`, and
`registry` on `store`'s in-memory folder and compares screens by deep equality. Turning a
`Screen` into DOM is the implementation's, entered from `modules/views/src/main.js`, the
build's entry; it is verified by demonstration and recorded as review rows (REQ-057 and
the criterion 1 row), never by a conformance test. Each operation belongs to one screen
kind and rejects on any other, so "not offered before a profile is selected" is a
property of the data, testable in Node, and the drawing has nothing to decide.

## Alternatives considered
### A simulated DOM as a development dependency (jsdom, happy-dom)
Rejected because: IMP-06 forbids a dependency without an instruction, and one was not
given; and a simulated DOM verifies the page against a simulation of Chromium when
criterion 1 exists precisely to test the real one under the target machines' policy.
Passing in jsdom would say nothing about the File System Access API, which is the risk.

### Running the conformance suite in Chromium (Playwright, Puppeteer, or the installed browser)
Rejected because: a browser driver is a dependency and a browser install the CI container
does not carry; the test command and `trace/results.xml` are Node's runner (DEC-003), and a
second runner would split the results the trace checker reads; and the slow, flaky half
of a browser suite would be spent on lists and forms, not on the one browser risk.

### A mount-only contract, `mount(container)`, with the suite reading the drawn DOM
Rejected because: it needs a DOM in Node, which is the first alternative again; and a suite
that asserts on elements and classes asserts on the drawing, so a redraw of the page would
fail conformance, which CORE-CON-002 says makes the test wrong. The screen data is what a
redraw must preserve; the elements are not.

### No conformance suite for views: every criterion by demonstration
Rejected because: criteria 2, 5, and 6 are exact behaviours (no data-changing call before
selection; one warning naming the other user; no message otherwise) that a hands-on session
checks once and a test checks on every change; HZ-008's "telling" half would have no
named, passing test to cite; and the null-double check (CORE-TST-002, rung 1) needs a
suite to fail.

## Consequences
- Makes easy: testing every SL-01 criterion but 1 and 3 in Node against the real modules;
  replacing the drawing wholesale (DEC-004 already expects it); the null double, which
  returns a fixed screen and fails every clause; composing later screens as more `Screen`
  kinds and more operations, each on one screen.
- Makes hard: any promise about the drawing itself (REQ-057's "prominently", a flag shown
  "wherever it is listed") is a demonstration row and a targeted read, not a test, so every
  screen slice carries one; the `Screen` shape is an Interface change to widen, so a new
  field on a screen is a CONTRACT session, not a redraw.
- Locks in: `Screen` as plain data, one operation per user action, each operation belonging
  to one screen kind; `src/main.js` as the one production caller of the surface.

## Reversal
Cost to undo: hours while only `views` 1.0 exists; days once every screen slice has added
its `Screen` kinds and operations, since the suite for each would be rewritten.
Would be triggered by: a requirement about the drawing that demonstration cannot hold
reliably from slice to slice, at which point a simulated DOM is instructed under IMP-06 and
the drawing gains its own suite beside this one; or the `Screen` data growing to mirror the
DOM element by element, which would mean the boundary is in the wrong place.
