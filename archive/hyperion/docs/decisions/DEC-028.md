# DEC-028: bowtie reads the registry itself, from the body and two ids, rather than drawing values a consumer assembles
Date: 2026-09-16
Status: proposed
Tier: interface

## Context
SL-08 needs a bow-tie that is "a pure function of the registry's data for one hazard on one
platform" (SL-08 scope), and HZ-011 is a diagram that differs from the stored data. DEC-004 names
`bowtie` a pure module beside `rating`, which imports only `baseline/types`. The registry already
exposes everything a bow-tie shows through two reads: `getHazardDetail` for the causal factors
and consequences, and `listPlatformHazards` for the controls, each with its kind and its state on
the platform (registry C-010, C-019, C-021). What the bowtie contract's operation takes decides
which module HZ-011's mitigation sits in, and `views` and SL-09's `reports` both call it, so
changing it later is an Interface change to three modules.

## Decision
`bowtie.bowtieFor(body, hazardId, platformId)` takes the working `DataBody` and the two ids, reads
them through `modules/registry/contract` and nothing else, and resolves with a `Bowtie` whose every
element is the registry's own value (bowtie C-001). `renderBowtieSvg` draws that value. The module
is still pure in DEC-004's sense: it reads no folder, storage, clock, or DOM and holds nothing
between calls (bowtie C-003). The one edge it adds is `bowtie → registry`.

## Alternatives considered
### bowtie takes values the consumer read (a `HazardDetail` and a `PlatformHazardRow`), importing no module
Rejected because: the check that the drawing matches the stored data would sit partly in every
consumer. A consumer could pass a detail of one hazard and a row of another, a row from a stale
body, or a row filtered for a screen, and bowtie could not tell. HZ-011's clause would then promise
only "draws what it is given", and `views` and `reports` would each need their own clause for the
rest. Keeping the read inside the module gives the hazard one mitigation clause and one
conformance test.

### Draw inside `views`, with no bowtie module
Rejected because: DEC-004 made `bowtie` a module so that SL-09's reports and `views` draw the same
diagram. Drawing it in `views` would mean `reports` either imports `views`, which nothing may
(DEC-004), or writes a second implementation.

### Store the layout or the SVG with the hazard, regenerating on change
Rejected because: REQ-059 forbids storing a diagram, and a stored drawing can go stale against the
records it depicts, which is HZ-011.

## Consequences
- Makes easy: comparing the drawing with the registry in one conformance test, with no consumer
  involved; `reports` at SL-09 using the same two calls as `views`.
- Makes hard: drawing a bow-tie of something that is not in a body (a draft, a hypothetical), and a
  bow-tie of a hazard on no platform, which REQ-059 does not ask for.
- Locks in: the edge `bowtie → registry`; a `registry` Interface change to `getHazardDetail` or
  `listPlatformHazards` now names `bowtie` among its consumers.

## Reversal
Cost to undo: hours. The bowtie contract, its suite, and its consumers (`views` at SL-08, `reports`
at SL-09) under CORE-CHG-001's Interface sequence. Nothing is stored, so no data changes.
Would be triggered by: a need to draw a bow-tie from values that are not in the body, or `registry`
splitting its reads so that two calls no longer describe a hazard on a platform.
