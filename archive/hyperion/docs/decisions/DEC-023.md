# DEC-023: A reference entry's links are refs on the entry, not rows in registry's link collection
Date: 2026-09-16
Status: accepted
Tier: interface

## Context
SL-10 criterion 3 and REQ-030 require a reference register entry to be linkable to any hazard,
causal factor, consequence, platform, control, or report, and criterion 4 with REQ-031 require
the entry to show everything it is linked to. The `reference-register` CONTRACT session had to
decide where that relationship is stored before it could write an operation for it.

Pivot already has a word and a shape for a stored relationship. `trace/requirements.yaml` says
"'link' is the one word for every stored relationship (hazard to platform, control to hazard,
control to platform, reference entry to anything)", and DEC-013 gave `registry` a `Link` record
in `collections.link` with three `linkKind` values for the first three of those. The obvious
reading is that a reference entry's links are a fourth `linkKind` in that same collection. That
reading cannot be taken, and the reason had to be recorded rather than left as an omission a
later reader would take for an oversight.

## Decision
A reference entry holds its links itself: `ReferenceEntry.links` is a `readonly RecordRef[]`,
each ref a `RecordKind` in `LINKABLE_KINDS` and an id, stored on the entry in
`collections['reference-entry']` and nowhere else (`reference-register` C-008, C-009).
`reference-register` writes no `Link` record and reads none, and `collections.link` stays
`registry`'s alone.

Baseline anticipated this. `RecordRef` is defined in `baseline/types.js` as "a reference to any
record, for links and log entries that cross record kinds", and the requirements its comment
cites are REQ-010, **REQ-030**, and REQ-045 — REQ-030 being this criterion. The shape this
decision uses is the one the baseline was given for it, so nothing in `baseline/` changes and
schema v1 stands with nothing stored changing shape.

## Alternatives considered
### A fourth `linkKind` in `registry`'s `collections.link`
Rejected because it makes `reference-register` a writer of another module's records. DEC-004
gives each record kind exactly one owning module, and `link` is `registry`'s: `registry` C-004
stores and validates every row of that collection and C-008 rejects "a `linkKind` outside the
three", so a fourth kind would either be refused by the module that owns the collection or
require `registry` to be taught a shape it holds no operation for. It would also put
`reference-register` and `registry` in a relationship DEC-004 decomposed the modules to avoid,
and it would drag `registry`'s `platformsAffected` (C-024) into answering for a kind it has no
link to.

### A new `reference-link` record kind with its own collection
Rejected because `RECORD_KINDS` is in `baseline/types.js` (DEC-005), so adding one is a Baseline
change under CORE-CHG-002 — the heaviest gate in the framework — for a relationship that one
module owns both the writing and the reading of. DEC-018 accepted that cost for
`review-schedule` because a schedule is a record in its own right with a tempo, a due date, and
a last-reviewed date, and because three fields on two other modules' records was the
alternative. A reference link has no fields of its own at all: it is a kind and an id. Spending
a baseline change on it would be ceremony with no reversibility to justify it (P1).

### A separate collection keyed by the record linked to, so the reverse direction is a lookup
Rejected because `DataBody.collections` is keyed by `RecordKind` (`baseline/schema.js`), so a
second collection of this module's own is not expressible without a second kind, which is the
alternative above. The reverse direction — what a hazard is linked to — is a scan of the
register, which is what REQ-047's filter at SL-11 does anyway and what `reference-register`
records as not promised at 1.0.

## Consequences
- Makes easy: linking with no cross-module write; listing everything an entry is linked to as a
  field read with nothing to join (C-009); a link surviving the record it names being deleted,
  because nothing resolves an id; the change log recording a link as an ordinary field change on
  the entry, with `links` before and after (`change-log` C-002), for a kind that module never
  had to be taught.
- Makes hard: the reverse direction. Asking what one hazard is linked to means scanning every
  entry's `links`, which is linear in the register rather than a lookup in a keyed collection.
  At DEC-003's scale that is accepted; if a screen at SL-11 needs it often, the answer is an
  index built by the consumer, not a second home for the fact.
- Locks in: the entry as the single home of its links, so there is no second place a link could
  be recorded and no two lists of one entry's links that could disagree. It also locks in that a
  link carries nothing — no kind, no note, no date of its own — beyond the ref; a link that needs
  a field of its own would be the `reference-link` kind rejected above.

## Reversal
Cost to undo: hours while only this contract exists and nothing has been implemented against it;
days once entries are stored, because every stored `links` array would have to be migrated into
whatever replaced it, which is a change to the shape of persisted data and so a STOP and a
Baseline change, not an Interface one.
Would be triggered by: a requirement that a link carry a field of its own — a kind, a note, who
made it, when — since a ref cannot hold one and the header of the entry describes the entry, not
the link; or a reverse-direction screen whose scan is too slow at real data volumes, which is
DEC-003's reversal trigger reached by another route.
