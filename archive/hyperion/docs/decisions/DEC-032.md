# DEC-032: A report is stored as what it held when it was produced, and its two documents are drawn from that record alone
Date: 2026-09-16
Status: proposed
Tier: interface

## Context
SL-09's G3 decision stores a produced report in the data folder "so REQ-026 and REQ-027 can be
answered later", and offers it as HTML and as Pandoc Markdown. Criterion 5 says a report "holds that
diagram as generated at the time of production". `reports` 1.0 can't define its record, its reads,
or its renders until it settles what the stored record holds and where the documents come from. A
report that re-reads the registry would answer "what did this report include" with today's data.

## Decision
A `Report` record holds what the report contained at the moment of production and names nothing it
reads again. That covers the template's name, title, and sections; the platform's id and name; one
`ReportHazard` per row of `registry.listPlatformHazards`, with each control's state and the
justification text; each omitted hazard and its reason; each bow-tie asked for, as the SVG text
`bowtie.renderBowtieSvg` gave; and each record that was past its review due date (`reports` C-003
to C-006). The documents are not stored. `renderReportHtml` and `renderReportMarkdown` are pure
functions of the record, plus `rating.ratingFor` for each residual's band, so the same report always
draws the same text (C-008). The band is not stored. The Markdown carries each bow-tie as an image
with a `data:image/svg+xml;base64,` source, so one file holds everything, as the HTML does (C-010).

## Alternatives considered
### Store references only (template id, platform id, hazard ids) and re-read at display
Rejected because it answers REQ-027 with what the records hold now, not what the report included,
and it can't hold criterion 5's diagram "as generated at the time of production". A hazard retired
since would drop out of an old report.

### Store the rendered HTML and Markdown texts in the record
Rejected because it keeps three copies of one report (the data and two drawings), which could
disagree (P3). The record could no longer answer REQ-027 without parsing a document. It would also
lock the drawings as first written, so correcting a render defect would need a data migration.

### Store the band beside the residual values
Rejected because a stored band is a copy of the matrix's answer, and HZ-010 is a band that differs
from the matrix. `rating` is pure and the matrix is baseline (DEC-002), so asking at draw time gives
the band the values have.

### Markdown with separate SVG files beside it
Rejected because it needs a write of several files, and `store` 4.0's `writeExportFile` writes one
(DEC-030). Whether the owner's pandoc-to-tectonic stack renders a `data:` SVG image is outside Pivot,
as SL-09's G3 decision puts rendering.

## Consequences
- Makes easy: REQ-027 and criterion 5 as comparisons against one stored value; downloading the same
  report twice gives identical text; a render defect is fixed without touching stored data.
- Makes hard: `data.json` grows with every report and every drawing it holds, and so does every
  backup (`reports` section 6).
- Locks in: the `Report` field shape as persisted data. Adding a field later is an Interface change;
  changing or removing one alters persisted data and needs a BASELINE-scale decision.

## Reversal
Cost to undo: days before any report is stored; after that, a data migration of every stored report.
Would be triggered by: `data.json` growing past what DEC-003's single file handles, or a ruling that a
report should reflect current data (which would contradict criterion 5).
