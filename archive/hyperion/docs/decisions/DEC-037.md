# DEC-037: Filtered lists are items against a platform, open items are grouped by platform, and an unlinked flag that cannot be read is null
Date: 2026-09-16
Status: proposed
Tier: interface

## Context
`views` 11.0 needs screens for SL-11. jay-pryor ruled the readings of its four criteria in
`docs/slices/SL-11.md`: a band is a hazard's residual on the platform it is listed against, and a
control's is the band of the row it is on; status is both record status and control state; the
dashboard's items are those on owned platforms, with awaiting controls only and in-progress
workflows on those platforms; a link counts whatever is at its other end. Three shapes those rulings
leave open had to be settled, each with an alternative seriously considered: what one item of a
filtered list is, how the open-items view avoids both dropping and hiding items, and what an
unlinked flag that could not be read looks like.

## Decision
A filtered list is a list of items, each a hazard or control listed against one platform's row, or
against none. A hazard on two platforms is two items, and a retired or deleted hazard, which no
platform's query shows, is one item against no platform (views C-045). Every filter is a predicate
on one item, so a filtered list is the unfiltered one less what fails, in the same order.

The dashboard and the open-items screen share one `PlatformItems` shape per live platform, built
the same way. The open-items screen adds `unplaced` for overdue reviews and in-progress workflows
on no live platform, and `unlinked` for criterion 4 (views C-046 to C-048).

`unlinked`, like `reviews` and `files`, is null when a read it depends on rejects. It is never
empty in that case (views C-048).

## Alternatives considered
### One item per hazard, carrying every platform it is on and each platform's band
Rejected because a band filter would then have to say whether a hazard matches on any platform or
on all of them, which the ruling does not say, and the result could not show which platform matched.
One item per hazard and platform makes "the platform it is listed against" literal.

### Open items as one flat list per kind, not grouped by platform
Rejected because the dashboard is grouped by platform (a change awaits a platform, not a user,
`change-log` C-012), and two shapes for the same items would let the two screens disagree about a
platform. With one shape, a platform's items on the open-items screen are deep-equal to its owner's
dashboard, which is testable.

### `unlinked` empty with an error message when a link cannot be read
Rejected because an empty list says every record is linked, which is what a malformed link would
hide. `reviews` null (C-031) and `files` null (C-035) already set the rule that a flag that could
not be read is not drawn as clear.

## Consequences
- Makes easy: criterion 1's "every item satisfies every active filter" as one predicate per item;
  criterion 3 as a comparison with the dashboard; criterion 4's clearing as a before-and-after of one
  list.
- Makes hard: a hazard on many platforms appears many times in the filter screen's hazards list.
  `openOpenItems` reads the links of every live record, so it costs a read per record (views
  section 6).
- Locks in: three screen kinds and three C-015 edges; items against platform rows as the unit of
  filtering.

## Reversal
Cost to undo: hours. The screens are `views`' and nothing depends on `views`.
Would be triggered by: hands-on use finding per-platform duplicates in the hazards list confusing,
or `openOpenItems` too slow on a real body, which would call for a `registry` read that answers
"linked" in one call.
