# DEC-035: Reports are prepared on a screen of their own before they are produced, made for the platform they are on, and downloaded from the report's screen
Date: 2026-09-16
Status: proposed
Tier: interface

## Context
`views` 10.0 needs screens for SL-09. To include a bow-tie (criterion 5), the user must see the
hazards the report will hold. The out-of-date warning (criterion 3) has to come before producing.
Three things had to be settled, each with an alternative seriously considered: how those two fit
before production, which platform a report's act is made for (it decides whose acknowledgement
queue the entry lands in, `change-log` C-010), and where the download of SL-09's G3 decision is
offered.

## Decision
`beginReport` shows a prepare-report screen with the template and platform picked, that platform's
hazards from the one `registry.listPlatformHazards`, and the out-of-date warning when
`reports.outOfDateFor` gives any record. Nothing is stored on that screen. `produceReport` takes
only the bow-tie hazards chosen from its rows, hands `reports` the list the screen showed, and
resolves with the report's own screen (views C-042). A report's `Act` is made for the platform the
report is on, as a workflow run on a platform is (DEC-026). `produceReport` is never gated, because
the entry reaches that one platform, so no owner's queue fills with "a report was produced".
Downloading is offered on the report screen in either form, through `store.chooseExportFile` and
`store.writeExportFile`, and is not a change (views C-043, DEC-030).

## Alternatives considered
### One call from the reports screen that shows a confirm screen only when data is out of date
Rejected because the user needs the platform's hazards to choose bow-ties before producing, and a
screen that appears only sometimes would put the bow-tie choice in two places. It would also make
"no warning is shown" a missing screen rather than a screen with no warning on it, which is harder to
test.

### `madeForPlatformId` null, so the report entry awaits the platform owner's acknowledgement
Rejected because a report changes no record the platform's owner reads. Its entry would sit in their
queue as noise and bury the changes REQ-012 exists to surface.

### Download offered immediately at production
Rejected because production would then mix a stored change with a browser picker. A cancelled or
failed write would then fall inside the act that stores the report. Downloading from the report
screen keeps the change and the write apart, and lets an old report be downloaded again.

## Consequences
- Makes easy: criteria 2, 3, and 5 on one screen whose data is compared with the query and with
  `outOfDateFor`; downloading any stored report at any time.
- Makes hard: producing a report is two operations rather than one.
- Locks in: the three screen kinds and four C-015 edges; a report's entry made for its own platform.

## Reversal
Cost to undo: hours. Screens are `views`' and nothing depends on `views`. The `madeForPlatformId` of
report entries already written stays as recorded.
Would be triggered by: hands-on use finding the two steps awkward, or an owner wanting report
production in their queue.
