# DEC-013: A control's kind belongs to its link to a hazard, and its platform link is the hazard-control-platform triple
Date: 2026-09-15
Status: accepted
Tier: interface

## Context
`registry` 2.0 is the record model SL-03 asks for, and three of its criteria turn on the
same question: where the facts that relate a control to a hazard and to a platform are
stored. Criterion 3 requires a control stored once in a library, linkable to any number of
hazards, and linkable separately to each platform a hazard is linked to, "so the same
control can be linked on one platform and not on another". Criterion 2 requires a hazard to
hold its preventative controls and its mitigating controls (REQ-044). REQ-032 requires the
library entry to be independent of hazards and platforms. Deciding this after the
conformance suite is written would be an Interface change to `registry` and to every
consumer, and the answer shapes stored data, so it is decided here and recorded.

`baseline/schema.js` holds one collection per record kind and `baseline/types.js` names one
`link` kind, so every link of every shape lives in `collections.link` keyed by a `LinkId`.
The question this record answers is not which collection, but what a link row carries and
what identifies it.

## Decision
Three link shapes share `collections.link`, told apart by a `linkKind` field that
`registry` owns under DEC-005:

- `hazard-platform`: the hazard, the platform, and the ID the hazard has in that platform's
  reports (REQ-051).
- `hazard-control`: the hazard, the control, and the `ControlKind` — `preventative` or
  `mitigating`. The kind is a fact about this hazard's use of the control, not about the
  control, so it is not a field of the library entry.
- `control-platform`: the hazard, the control, and the platform, together. A control is
  linked on a platform *for a hazard*; the triple is the identity of the link, and the pair
  (control, platform) is not.

A library `Control` therefore carries its title and its header and nothing else: no hazard,
no platform, no kind. REQ-001 ("show a control as linked to a platform only when a stored
link between that control and that platform exists") is kept by the existence of a triple
naming that control and that platform.

## Alternatives considered
### `ControlKind` as a field of the library `Control`
Rejected because: the same control is preventative against one hazard's causes and
mitigating against another hazard's consequences, and a bow-tie (SL-08) draws it on the
side the hazard puts it on. A single stored kind forces a second library entry for the
same control, which is REQ-032 broken to store one enumerated value, and the two entries
then drift.

### `ControlKind` as a field of the `control-platform` link
Rejected because: it makes a hazard's control list per-platform, so criterion 2 — a hazard
holding its preventative and mitigating controls — could not be answered without naming a
platform, and a control linked to a hazard on no platform yet would have no kind at all.

### The platform link as the pair (control, platform), with no hazard
Rejected because: a control shared by two hazards on one platform would then be linked for
both the moment it is linked for either, which is the silent inheritance HZ-001 names, and
criterion 3's "linked separately" would be unfalsifiable. It also leaves REQ-058 (SL-04)
with nowhere to hang a per-hazard justification for leaving the control unlinked.

### One link row carrying an optional platform, covering both the hazard-control and the control-platform cases
Rejected because: the two rows mean different things — one says the control belongs to the
hazard's bow-tie, the other says this platform has it — and a single shape with an optional
field makes "linked to the hazard but on no platform" and "linked on a platform" the same
query with a null check, which is how one of them eventually gets counted as the other.

## Consequences
- Makes easy: a control edited once and read the same way by every hazard and platform;
  unlinking a control on one platform without touching another; a per-hazard justification
  hanging off the triple at SL-04; a bow-tie reading the kind straight off the
  hazard-control link.
- Makes hard: asking "is this control on this platform" without naming a hazard — the
  answer is "for which hazard", which is the question REQ-001 is really asking; and a
  control library that wants to be a taxonomy of preventative and mitigating measures.
- Locks in: three `linkKind` values in stored data; the triple as the unit of a platform's
  control links, so a justification, a confirmation (REQ-013, REQ-070), and a review all
  key on it.

## Reversal
Cost to undo: days. Every stored link row would be reshaped and `registry`'s contract, its
conformance suite, and `views` migrated under CORE-CHG-001's Interface sequence; data folders
already holding links would need converting, which the pair-shaped alternative cannot do
without asking a user which hazard each link was for.
Would be triggered by: the organisation deciding a control is preventative or mitigating in
itself, independently of the hazard it sits on, which would move the kind to the library
entry and collapse the hazard-control link to a plain membership.
