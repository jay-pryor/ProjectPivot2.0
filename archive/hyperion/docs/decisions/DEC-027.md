# DEC-027: A workflow is reached from a register of its own, and every changing workflow operation is gated on the platforms its subject reaches
Date: 2026-09-16
Status: accepted
Tier: interface

## Context
`workflows` 1.0 owns the five guided workflows, their step lists, the gates, and the completion,
and DEC-025 made a workflow a stored record from its first step so that REQ-039 has something to
protect and REQ-049 has something to read. It exposes no screen. `views` 8.0 is the version that
shows one, and it cannot be written without two questions being answered that no acceptance
criterion of SL-07 settles.

Where a workflow is started and reached again. SL-07 criterion 1 asks that each workflow be
presented as a sequence of named steps with the current step, the steps done, and the steps
remaining visible, and says nothing about how a user gets to one. SL-07 puts "the dashboard's list
of in-progress workflows" out of scope, at SL-11 under REQ-049. If `views` 8.0 offers no list at
all, a workflow stored across a save and a load is unreachable until SL-11 and DEC-025's reason
for storing it early is unusable in the built application for a slice and a half.

Whether a workflow operation is gated by C-027. REQ-011 is allocated to `views` C-027: before
saving an edit that changes the stored content of a hazard, control, or justification linked to
more than one platform, every such platform is listed and proceeded past. Four of the five
changing workflow operations change the stored content of a hazard through the acts their steps
make — `add-data`'s `describe-the-hazard` and `choose-controls` call
`registry.addCausalFactor`, `addConsequence`, and `linkControlToHazard`, which are three of the
four operations C-027 already gates on the hazard screen — so the requirement reaches this
surface whatever is decided about the workflow record itself. The fifth, and `advanceStep` and
`abandonWorkflow`, change only the workflow record, which REQ-011 does not name, exactly as
DEC-021's review schedule and DEC-024's reference entry did not.

## Decision
**A register of workflows is a screen of its own, reached from the hazards screen, listing every
live workflow the working body holds.** It is `workflows.listWorkflows` whole, in that contract's
order, filtered by nothing and sorted by nothing, with the platforms a new workflow may be started
on; one workflow's own screen is reached from it and returns to it, as the reference register and
one entry's screen are (`views` C-036, C-037). This is the same shape as C-028: the whole history
is one screen and a per-record view is a later version's, so the whole register is one screen and
the active profile's in-progress subset is REQ-049's at SL-11. Nothing here is filtered by profile
or by state, so SL-11 adds a view rather than replacing one.

**Every changing workflow operation is gated on `registry.platformsAffected` of the workflow's
subject, and `views` C-027 states outright the invariant it has kept since 5.0: an operation is
gated exactly when the entry its act appends carries two or more platform ids.** DEC-026 gives the
change-log entry of every workflow operation `platformsAffected` of the record's `subject`, so
gating on that same ref, on the same body, is the same derivation and not a second one that could
disagree — which is the property C-027 exists for and the one SL-05's criteria 3 and 4 cannot be
allowed to differ on. In fact the gate can fire only on an `add-data` workflow whose hazard has
been linked to two or more platforms since the run began: a `platform` subject reaches the one
platform it names and a subject not yet created reaches none, so four of the five kinds never
gate, and `startWorkflow` never gates at all and gets no `PendingEdit` variant. `views` C-027
gains four variants, one per operation of the workflow screen, and `confirmEdit` makes the one
`workflows` call the gated operation would have made.

## Alternatives considered
### No register: start a workflow from the hazards screen and hold the running one in the app
Rejected because: a workflow saved and loaded again would be unreachable. DEC-025 stored the
record from its first step precisely so that a half-finished review survives closing Pivot, and a
surface with no way back to it makes that storage invisible until SL-11 — the user would see an
entry in the change log for a workflow they cannot open. It also gives criterion 4's refusal
nowhere to be seen: a completed workflow's record is only readable on a screen that lists it.

### Let the register be the dashboard's in-progress list, filtered by profile and state
Rejected because: SL-07 puts that list out of scope and REQ-049 allocates it at SL-11 beside
overdue reviews and unconfirmed controls. Building it here would write two thirds of an SL-11
screen inside an SL-07 contract, and a filtered list is the wrong default for the only way to
reach a workflow — a user who is not the one who started a run still has to be able to open it,
and criterion 4's sealed record is read by whoever reads the data.

### Gate `submitStep` alone, and leave the other four ungated
Rejected because: `advanceStep`, `completeWorkflow`, and `abandonWorkflow` each append a
change-log entry carrying `platformsAffected` of the subject (DEC-026, `workflows` C-010), so on an
`add-data` workflow whose hazard is on two platforms each would put an entry in two owners'
acknowledgement queues that the user was never warned about. That asymmetry between what is warned
about and what awaits acknowledgement is the one thing C-027 exists to prevent, and it is the same
objection DEC-021 and DEC-024 raised against leaving a review schedule and a reference entry
ungated. The cost of rejecting it is three `PendingEdit` variants and a confirm-edit screen
between two steps of a guided sequence in the one case that can reach it.

### Gate nothing, on the ground that a workflow record is a kind REQ-011 does not name
Rejected because: it is true of the workflow record and false of what the steps do. A
`describe-the-hazard` submission calls `registry.addCausalFactor` on a hazard that may be on
several platforms, which is REQ-011's own words; leaving it ungated would put the requirement's
one allocated clause in the position of holding on one screen and not on another for the same act.

### Gate `completeWorkflow` on the union of the platforms every record it reviews reaches
Rejected because: it is the second derivation DEC-026 refused. A completion's `completeReview`
calls each carry `affectedPlatformIds` that `workflows` derives per record (DEC-026), and `views`
computing a union of its own would show the user a list that no entry of the act it gated carries
— warning about platforms while a different list awaits acknowledgement, which is exactly the
disagreement the gate is supposed to make impossible. Gating on the subject keeps one ref, one
call, one list.

### Show a review workflow's omitted hazards from `workflows.reviewOmissions`
Rejected because: `views` C-020 already requires every screen that lists a platform's hazards to be
built from one `registry.listPlatformHazards`, and that result carries `omitted`. Calling
`reviewOmissions` as well would ask two contracts the same question on one screen, and
`reviewOmissions` derives its answer from the same query anyway (`workflows` C-006). It stays
`workflows`' own read, for a consumer that wants the omissions without the rows, and this surface
calls it at no version.

## Consequences
- Makes easy: reaching a workflow saved by an earlier session; seeing criterion 4's refusal, which
  needs a screen that shows a complete record; one statement of when an operation is gated, with
  no kind-by-kind exception list; SL-11's dashboard, which adds a filtered view over a register
  that already exists.
- Makes hard: a quiet `add-data` run on a hazard that is on several platforms — every submission,
  every advance, the completion and the abandonment each show the confirm-edit screen. Reducing
  that noise means either not gating the operations that change only the workflow record, which is
  the rejected alternative, or not letting a workflow's subject hazard be linked mid-run, which no
  contract forbids.
- Locks in: `views` → `workflows` as an edge in the dependency graph; `registry.platformsAffected`
  as the only source of an affected platform in this module, as DEC-017, DEC-024 and DEC-026 have
  it; four `PendingEdit` variants and no edit operation on a workflow record at any version, since
  adding one would reopen REQ-039.

## Reversal
Cost to undo: hours while no implementation exists. The register is C-036 and two rows of C-002
and C-015; the gate is one paragraph of C-027, four `PendingEdit` variants, and one
`platformsAffected` call per changing workflow operation. Nothing is stored differently either
way: a change-log entry's `affectedPlatformIds` is DEC-015's shape and is derived by `workflows`
whether or not this module gated on the same ref. Days once a conformance suite exists, since the
gate is asserted per operation.
Would be triggered by: SL-11's dashboard arriving and making the register redundant, which would
be the moment to ask whether the unfiltered list should stay; or a run where the `add-data` gate
fires often enough to be reported as noise, which would move the decision to the rejected
alternative and put one exception back into C-027.
