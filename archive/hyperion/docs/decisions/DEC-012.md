# DEC-012: Every module operation is asynchronous, `rating` included
Date: 2026-09-15
Status: accepted
Tier: interface

## Context
`rating` is the first pure module to get a contract (DEC-004: "two pure modules
(`rating`, `bowtie`)"). Every operation of `store`, `profiles`, `registry`, and `views` is
asynchronous because each does I/O or composes something that does. `ratingFor` does none:
it is a lookup of one of 35 table cells. Writing it synchronously would read better and
would say in the signature that it cannot block. Deferring the question is not possible:
the shape is the contract, and `views` and `reports` call it from SL-03 on, so changing it
later is an Interface change to `rating` plus every consumer.

## Decision
`rating.ratingFor` returns a promise, like every operation of every other Pivot module, and
signals a value outside the scales as a rejected promise carrying a named error class. The
contract states separately that the operation is a pure total function of its two arguments
(`rating` C-004), so purity is promised by a clause and a conformance test rather than
inferred from the absence of `async`.

## Alternatives considered
### A synchronous `ratingFor`, with the implementation selected by a top-level `await` in `contract.js`
Rejected because: it puts a top-level await in a runtime source that `scripts/build.js`
inlines into the single `pivot.html` (DEC-003), which makes the whole page's module graph
wait on it, for one function that never blocks; and it splits error signalling at the
module boundary, so `views` would handle a thrown `ConsequenceOutOfScaleError` from one
module and a rejected promise from the other four when the two arrive in the same render.

### A synchronous `ratingFor` with a static `import './src/rating.js'`, and no null double
Rejected because: it drops this module out of CORE-TST-002 rung 1. A conformance suite that
cannot be shown to fail against a trivial implementation is assumed to be a control, and
this is the suite that carries HZ-010 — the one suite in the project least worth taking on
trust.

### Both: a synchronous `ratingFor` beside the asynchronous one
Rejected because: two ways to ask the same question is a second implementation of something
that already exists, and a caller that reaches for the synchronous one inside a render
loop is exactly the coupling C-004 exists to make unnecessary.

## Consequences
- Makes easy: one error shape at every module boundary; `rating` joining the existing null
  double and implementation-selection pattern with no new mechanism; `views` awaiting a
  list of hazards' ratings alongside everything else it awaits.
- Makes hard: calling a rating from a place that cannot await - a synchronous comparator, a
  template expression. A consumer that needs many ratings resolves them before rendering.
- Locks in: `Promise` in the return type of every Pivot module operation, which is what
  makes the rule a rule rather than four coincidences.

## Reversal
Cost to undo: hours (this contract, its conformance suite, and each consumer the manifests
name - `views` at SL-03, `reports` at SL-09), under CORE-CHG-001's Interface sequence.
Would be triggered by: a render path measured as spending materially more on awaiting
ratings than on drawing them, which C-004's purity would let a consumer fix by resolving
them once instead.
