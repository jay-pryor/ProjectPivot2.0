# DEC-020: The platforms a schedule change reaches are named by the caller, as they are for the change log
Date: 2026-09-16
Status: accepted
Tier: interface

## Context
Every changing operation of a record module records its own act through `change-log`
(DEC-016, registry C-023), and an entry carries `affectedPlatformIds`: every platform the act
reaches, which is what decides whose queue it lands in (`change-log` C-010; HZ-006).
`review-schedule` 1.0 has two changing operations, `setSchedule` and `completeReview`, so it
has to supply that list or leave a change to a hazard's review tempo unrecorded, which C-012
and HZ-005 forbid.

It cannot compute the list. A schedule names its record by a `RecordRef` and the platforms a
hazard or a control reaches are a derivation from `registry`'s links
(`registry.platformsAffected`, registry C-024). Importing `modules/registry/contract` to ask
is the record-module-to-record-module edge DEC-004 decomposed the modules to avoid, and
DEC-018's reversal trigger names it as a STOP and a re-examination of that decomposition
rather than a widening to be taken quietly in a CONTRACT session.

## Decision
`review-schedule`'s `ScheduleAct` is registry's `Act` — `profile` and `madeForPlatformId` —
plus `affectedPlatformIds`, which the caller supplies. It is stored on the entry as given and
checked only for shape: this module never asks whether a platform exists, whether the act
truly reaches it, or whether `madeForPlatformId` is among them. `views` computes it from
`registry.platformsAffected` for the record being scheduled, which is the same call it
already makes to list the platforms an edit reaches before making it (views C-027).

This is DEC-015's arrangement one layer up. `change-log` sits below every record module and
cannot ask which platforms a change reaches, so its caller names them; `review-schedule`
schedules records it does not own and cannot ask either, so its caller names them too. The
module that holds the links is the one that answers, and it answers to `views`.

## Alternatives considered
### `review-schedule` imports `modules/registry/contract` and calls `platformsAffected`
Rejected because: it is a record module depending on another record module (DEC-004), and
DEC-018 recorded that discovering this need is a STOP, not a licence. It would also be
incomplete by construction: `reference-entry` is schedulable at 1.0 and `registry` holds no
link to one, so the edge would answer for three of the four kinds and the caller would still
have to answer for the fourth.

### An empty `affectedPlatformIds` on every schedule change
Rejected because: it means no platform ever awaits a change to a review tempo, so an owner
reading a platform would never learn that the review schedule of a hazard on it had been
changed or a review recorded against it. HZ-006's never-statement is about data of a hazard
linked to a platform changing through an edit made for another platform without that
platform's owner seeing it, and a due date is such data. Storing a list this module knows to
be wrong is worse than requiring the caller to pass the right one, which `views` can.

### `madeForPlatformId` alone, with `change-log` treating it as the whole reach
Rejected because: it conflates the platform a user was working on with the platforms a change
reaches, which DEC-016 separated for the reason that an edit made on a platform-independent
screen reaches every platform and is made for none. A schedule set from a hazard's own screen
is exactly that case.

## Consequences
- Makes easy: the module graph, which gains one edge to `change-log` and no other; a fourth
  schedulable kind whose records no module owns yet; a conformance suite that needs no
  `registry`.
- Makes hard: a consumer other than `views` calling `setSchedule` correctly, since it must
  know to ask `registry` first; and any guarantee of completeness, which this contract cannot
  give and says so in its not-promised section, as `change-log`'s does.
- Locks in: the caller as the source of a change's reach, for every record module below the
  screen.

## Reversal
Cost to undo: hours, by dropping the field and computing it, but only together with the
`registry` edge DEC-018 makes a STOP, so the real cost is that re-examination.
Would be triggered by: a third consumer of `setSchedule` appearing, so that the obligation is
duplicated in two places rather than held once in `views`; or `platformsAffected` moving out
of `registry` into a module every record module may depend on.
