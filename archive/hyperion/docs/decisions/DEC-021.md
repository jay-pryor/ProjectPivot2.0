# DEC-021: Setting a review tempo is gated by the list of platforms it reaches, like an edit to the record itself
Date: 2026-09-16
Status: accepted
Tier: interface

## Context
`views` 5.0 C-027 gates five operations: an operation whose `registry.platformsAffected` gives
two or more platforms resolves with the confirm-edit screen listing them, changes nothing, and
waits for `confirmEdit`. That is REQ-011's half of HZ-006, whose never-statement is severity 1.

`views` 6.0 adds one changing operation, `setReviewTempo`, which sets the review tempo and due
date of a hazard, a control, or a platform through `review-schedule.setSchedule`
(SL-06 criterion 1). A hazard's due date is data every platform the hazard is linked to reads,
and `review-schedule`'s `ScheduleAct` requires `affectedPlatformIds`, which `views` computes
from `registry.platformsAffected` for the record being scheduled (DEC-020). So the call that
decides whether to gate is already being made for another reason; what had to be decided is
whether its result gates.

REQ-011 says "the stored content of a hazard, control, or justification linked to more than one
platform". A review schedule is none of those three: DEC-018 gave it a record kind of its own
rather than three fields on `registry`'s records, so on REQ-011's words a tempo change is
outside the gate. That reading and the general sentence C-027 opens with — "an edit that
reaches more than one platform lists them and waits for the user" — do not agree, and a
contract cannot hold both.

## Decision
`setReviewTempo` is the sixth gated operation. When `registry.platformsAffected` for
`fields.ref` gives two or more platform ids, the call resolves with the confirm-edit screen
carrying a sixth `PendingEdit` variant and changes nothing until `confirmEdit`; when it gives
one or none it proceeds, which is every `platform` ref and a hazard or control on at most one
platform. C-027 therefore keeps one rule with no exception, and the list the user is shown is
the same list `views` then passes as the act's `affectedPlatformIds`, so what a user was warned
about and what then awaits acknowledgement are one value rather than two derivations that
agree.

DEC-018 chose where a tempo is stored. It did not decide what a user is told before changing
one, and it should not: the same act, warned about under the rejected storage and silent under
the chosen one, would make a decomposition decision reach the screen.

## Alternatives considered
### `setReviewTempo` is not gated, on REQ-011's literal scope
Rejected because: it makes C-027 a rule with an exception, and the exception is the one
operation whose record kind was invented after the clause was written — the shape a later
reader would most reasonably take for an oversight. HZ-006 is severity 1, the gate already
exists, and the cost of firing it is one screen the user proceeds past. REQ-011 is not narrowed
by this: it is satisfied by C-027 as before, and the sixth operation is a promise beyond it,
recorded here so it is not read as one.

### Gate on `madeForPlatformId` instead — gate only when the tempo is set from a screen holding a platform
Rejected because: a tempo is set from the hazard, controls, and platforms screens, none of
which holds a platform (C-026), so the gate would never fire. It also repeats the conflation
DEC-016 separated: the platform a user was working on is not the platforms a change reaches.

### Gate `completeReview` the same way
Rejected because: `views` 6.0 has no operation that completes a review. The last reviewed date
moves only through `review-schedule.completeReview`, which `workflows` calls at SL-07
(SL-06 criterion 3); whether that act is gated is SL-07's to decide, on a screen this version
does not have.

## Consequences
- Makes easy: one rule for every edit that reaches more than one platform, checkable by one
  conformance case per gated operation; the warned list and the act's `affectedPlatformIds`
  being the same value for `setReviewTempo`, which C-027 has to argue for the other five.
- Makes hard: setting a tempo on a hazard linked to many platforms, which now takes two calls;
  and the `PendingEdit` union, which gains a variant whose record is named by a `RecordRef`
  rather than carried as a record.
- Locks in: the gate as a property of how far a change reaches, not of which record kind it
  changes. A seventh changing operation is gated unless a decision record says otherwise.

## Reversal
Cost to undo: hours — drop the variant and the gate from `setReviewTempo`'s clause, an
Interface change to `views` with no stored data affected.
Would be triggered by: a targeted read or a hands-on session finding the gate fires so often on
tempo changes that users proceed past it without reading, which would weaken it for the five
operations that need it most.
