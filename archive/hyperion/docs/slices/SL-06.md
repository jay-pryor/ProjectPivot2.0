# SL-06: Review schedule - tempo, due date, last reviewed, and the overdue flag
Order: 6 · Risk: medium

Acceptance criteria drafted by claude-fable-5-1 at G3 for jay-pryor to accept or rewrite;
they are not human-written until that review is recorded.

## Scope
HZ-012 (2C, Serious) and HZ-009 (2D, Medium), behind `review-schedule`. A user sets a
review tempo per hazard, control, platform, and reference entry; the due date is the
schedule's next fall-due and is never derived from the last reviewed date; the last
reviewed date moves only when a review workflow completes; anything past due is flagged
wherever it is listed. Two questions G1 deferred here (REV-002 M21) are settled by this
slice's contract.

Layers: review-schedule, views (the tempo field, the dates, the overdue flag on every
list). The clock is the baseline's, fixed by test.

## Acceptance criteria
1. A review tempo can be set for each hazard, control, platform, and reference entry
   individually, and is stored with the persistent data, so it survives save and load.
2. The review due date is the date the user-set schedule next falls due. Changing the
   last reviewed date, by any route, does not move the due date.
3. The last reviewed date is set to the current date only when a review workflow on the
   record is completed. Editing the record does not set it. `review-schedule` exposes
   the completion operation; a test calls it here and `workflows` calls it in SL-07.
4. With the clock fixed to a date past a record's due date, the record is flagged overdue
   in every list that shows it; with the clock fixed to the due date or earlier, it is
   not. The boundary is the one decided below.

## Decided at the CONTRACT sessions (DEC-019, DEC-020, DEC-021)
Three questions the G3 rulings left open, each settled with its rejected alternative recorded.

- Month arithmetic where the day does not exist: a tempo that lands on a day the target
  month does not have clamps to that month's last day, and the day of the month does not
  recover on later advances (31 January, tempo 1: 28 February, then 28 March). Rejected:
  overflow into the following month, which contradicts "the same day of the month"; and a
  stored anchor day, which is a second field that can disagree with the due date.
- The platforms a schedule change reaches are named by the caller in the act, not derived.
  `review-schedule` holds no link and does not import `registry`, which DEC-018's reversal
  trigger names as a STOP. Rejected: the `registry` edge; an empty list, which would leave a
  platform's owner never told (HZ-006).
- Setting a review tempo is gated by the list of platforms it reaches, like an edit to the
  record itself: `views` C-027 gains a sixth operation. REQ-011 names "the stored content of a
  hazard, control, or justification", and a schedule is a record of its own kind (DEC-018), so
  this is a promise beyond that requirement rather than a reading of it. Rejected: leaving it
  ungated on REQ-011's literal scope, which would make C-027 a rule with one exception, and
  the exception the one operation whose record kind was invented after the clause was written.

## Decided at G3 (jay-pryor, 2026-09-14)
The first two were deferred from G1 (REV-002 M21, carried as FND-021, which closes when
the `review-schedule` contract records the clauses).

- Tempo unit: a whole number of calendar months, with the due date the same day of the
  month, so "every 12 months" reads as it is meant. Rejected: a whole number of days,
  simpler to compute but harder to read.
- Overdue boundary: overdue from the day after the due date, so a review done on the due
  date is on time. Rejected: overdue on the due date itself.
- "Next falls due": a user-set next-due date, advanced one tempo each time a review
  workflow completes. Rejected: a user-set start date plus n tempos.

## Out of scope
The review workflow's steps (SL-07). The out-of-date warning before a report (SL-09).
Overdue items on the dashboard (SL-11).

Three gaps the CONTRACT sessions found and did not close, recorded here and in
`modules/review-schedule/CONTRACT.md` section 7 and `modules/views/CONTRACT.md` section 7 so
none is discovered late:

- HZ-009 cannot be verified at this slice. Its never-statement is about a report produced
  from out-of-date data without the user being told, and the telling is REQ-016, which this
  slice puts out of scope. `review-schedule` 1.0 supplies what a report needs to tell it
  (C-006, C-009) and nothing that warns. `trace/slices.yaml` claims HZ-009 for SL-06, and an
  accepted slice may claim only verified hazards (CORE-TRC-002), so that claim must be
  narrowed or moved to SL-09 at a GATE session before this slice can be accepted.
- REQ-015 names ten record kinds; criterion 1, REQ-021, REQ-022, and REQ-072 name four, and
  four is what `SCHEDULABLE_KINDS` holds at 1.0. The six others — causal factor, consequence,
  justification, rating, report, workflow record — carry no schedule and so no last reviewed
  date. Widening the set is an Interface change, expected at SL-07 or SL-09. `reference-entry`
  is not a gap: `review-schedule` resolves no id, so it is schedulable now although no module
  owns that kind until SL-10.
- REQ-023 names controls, platforms, and reference documents, and `views` 6.0 flags a control
  and a platform. No screen of this version shows a reference entry, because no module owns that
  record kind until SL-10 and `registry.platformsAffected` would refuse a ref of it, so the
  reference-document half of REQ-023 is verified at SL-10 and not here. `SCHEDULABLE_KINDS`
  needs no change for it; `views` does, which is an Interface change to `views` at that slice.
