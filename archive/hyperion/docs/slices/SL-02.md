# SL-02: Data integrity - integrity check, backups, restore, crash recovery, and what is said when a save or load fails
Order: 2 · Risk: high

Acceptance criteria drafted by claude-fable-5-1 at G3 for jay-pryor to accept or rewrite;
they are not human-written until that review is recorded.

## Scope
Everything HZ-003 (2C, Serious) rides on, all of it behind `store`'s contract, which G2
named the most important interface in the project. The save path gains an integrity
check, hourly backups with a 72-deep ring, restore with a warning, a browser-storage
mirror of the working state with recovery on opening, and the messages that say what
was not saved and what could not be read.

Layers: store, views (the messages and the restore and recovery prompts). The clock is
the baseline's, fixed by test.

## Acceptance criteria
1. Every file Pivot writes carries an integrity check written with it. On opening a data
   folder, Pivot checks every file it wrote there: the stored data, the profiles, every
   kept backup, and every superseded save. A file altered outside Pivot fails its check,
   and Pivot names that file and tells the user which data is affected before showing
   anything from the folder. A failed stored data or profiles file means nothing from that
   file is shown; a failed backup or superseded save is reported and the stored data is
   still shown after the message.
2. A save that stops partway, at a fault point armed by a test, leaves the previously
   saved data readable and unchanged, and tells the user which changes were not saved,
   naming them. (REV-002 M3, rejected at G1 as implementation-level, is taken up here as
   a contract promise: a save replaces stored data whole or not at all.)
3. With the clock fixed: when the working state changes, saved or not, and more than an
   hour has passed since the newest kept backup, a backup of the working state as changed
   is written at once. A change within the hour writes no backup, and neither does opening,
   saving, or restoring without a change. Writing the 73rd backup deletes the oldest, and
   never a newer one.
4. Restoring from a kept backup, or from a save state file a user chose, first warns
   that the current stored data will be replaced and proceeds only on confirmation; the
   data loaded afterwards equals the backup's contents. A backup and a save state file
   restore through one path, because they share one format.
5. Every change to the working state is mirrored to the browser's storage. When Pivot is
   opened and that storage holds working state never saved to the folder, Pivot offers to
   recover it; accepting restores that state, declining discards it, and either way the
   folder is untouched until the user saves. One person uses Pivot per machine (ASM-006),
   so the browser's copy is not told apart by folder or by user.

## Decided at G3 (jay-pryor, 2026-09-14)
- The integrity check is a content hash written inside each file. The backup ring lives
  in a `backups` subfolder of the data folder. Both are persisted shape, so the BASELINE
  session writes them into the schema.
- The hour in REQ-062 is measured from the last backup's recorded stamp. Machine clocks
  are assumed correct for AEST (ASM-005), so the write time would give the same answer;
  the stamp is the one a test can fix.

## Decided at the store CONTRACT session (jay-pryor, 2026-09-15)
- Criterion 3: a backup is triggered by any change to the working state, saved or not, once
  more than an hour has passed since the newest backup, and holds the working state
  (DEC-008). "More than an hour" is REQ-062's; REQ-062's "stored data" wording lags this
  ruling and is reworded at a GATE session.
- Criterion 1: opening checks every file Pivot wrote, backups and superseded saves
  included; only a failed stored data or profiles file stops those data from being shown.
- Criterion 5: one person per machine (ASM-006); the mirror is one `localStorage` key
  (DEC-009).

## Decided at the views CONTRACT session (jay-pryor, 2026-09-15)
- Criterion 1: when only a kept backup or superseded save fails, the failures are shown on
  a check screen of their own, acknowledged before the profile screen, so nothing from the
  folder is shown before the message (views C-010). The alternative, the messages on the
  profile screen beside the profile list, was set aside as not "before".
- Criterion 5: recovery is offered after a profile is selected, before the hazards screen,
  so nothing but a profile is written before selection (views C-002, C-013). Offering it on
  the profile screen at opening was set aside.
- Criterion 4: the warning before a restore also names the unsaved changes the restore
  would discard (views C-014), not only that the stored data will be replaced.
- A folder whose stored data or profiles file fails its check cannot be restored or
  recovered in Pivot: store 2.0's `restore` and `recoverWorkingState` need a completed load.
  No criterion requires it; views 2.0 lists it as not promised and FND-039 holds it for a
  later store change.
