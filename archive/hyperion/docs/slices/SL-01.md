# SL-01: Walking skeleton - open from the shared folder, pick a profile, save and load, second user's save detected
Order: 1 · Risk: high

Acceptance criteria drafted by claude-fable-5-1 at G3 for jay-pryor to accept or rewrite;
they are not human-written until that review is recorded.

## Scope
The riskiest end-to-end path G2 named at REV-004: whether a page opened from the shared
folder can read and write that folder under the target machines' browser policy (ASM-001),
and whether two users' saves on one shared folder can be told apart with nothing but files
(REQ-014, REQ-071). The G2 map that listed these risks is retired by DEC-011. Cuts through every layer as thinly as possible: the `baseline/` build script
produces one `pivot.html`; opened from the shared folder in a Chromium browser on a target
machine, it chooses the data folder, requires a profile, shows it in the top bar, creates
one hazard with a global ID, saves it, loads it back equal, and detects that a second copy
of Pivot saved in between. If the File System Access API cannot reach the folder under the
target machines' browser policy, `store` changes shape and the baseline with it, and this
slice is where that is found (DEC-003 reversal trigger, ASM-001).

Layers: baseline (build, types, persisted schema, clock), store, profiles, registry (one
record kind only), views (folder picker, profile screen, top bar, one hazard form).

## Acceptance criteria
1. A `pivot.html` built by the checked-in script, copied next to the data folder on a
   company Windows machine with no administrator rights and nothing installed beyond a
   Chromium-based browser, opens, lets the user choose that folder, and reads and writes
   it. Demonstrated on a target machine and recorded as a review row that REQ-040 and
   REQ-041 cite.
2. On opening, Pivot lists the profiles stored in the data folder with none pre-selected,
   whatever profile was used last, and lets the user create a new profile. Until a profile
   is selected, no operation that changes stored data is available.
3. The active profile's name is visible in the top bar of every screen this slice draws.
   Recorded as a review row that REQ-057 cites.
4. A hazard created with a title, saved, and loaded after Pivot is closed and reopened
   from the same folder holds the same field values and the same global ID. A global ID,
   once assigned, is never assigned again, including after the hazard is deleted.
5. When copy B loads the data, copy A then saves, and copy B then saves: B is told that
   another user saved since B loaded; the data as A saved it is written into a
   `Superseded Saves` subfolder of the data folder before B's data is written; afterwards
   the data folder holds B's data and the subfolder holds A's.
6. When no other copy has saved since loading, a save writes nothing to
   `Superseded Saves` and shows no such message.

## Decided at G3 (jay-pryor, 2026-09-14)
- How `store` tells that another user saved since this user loaded, with nothing but
  files (G2 risk 2): a save stamp written with the data, holding the saving user
  profile's ID, the AEST time, and a random token, and compared on save. The `store`
  CONTRACT session writes the clause.
